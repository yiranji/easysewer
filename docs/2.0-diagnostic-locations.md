# Semantic diagnostic locations

`Diagnostic.subject` identifies a collection, a scalar or composite key, and a
tuple field path. String attributes and integer sequence positions retain their
types. `related` lists other subjects involved in the rule. A local validator
may supply a subject with only a path; the owning collection binds its namespace
and key. Display fields such as `object_id` and `field` are not parsed to guess
an object from a different collection.

```python
report = model.validate(for_run=True)
for issue in report.errors:
    print(issue.code, issue.subject)
    for location in issue.locations:
        print(location.status, location.original, location.spans)
```

Locations refer to the original retained INP, with its SHA-256. `current` means
that the addressed value and identity still match an explicitly covered source
field. `changed` retains historical declarations without attributing them to the
new value. `context` identifies a record or descendant declarations without
claiming a single exact value token. `omitted`, `unknown`, `untracked`,
`programmatic` and `absent` explain why an exact source cannot be supplied.
Sequence-item paths remain untracked because tuple positions are not persistent
identities. Changing a variant likewise does not establish correspondence merely
because the new variant has a field with the same name.

Missing references inside a sequence also relate the container before the first
integer index. For example, an unresolved REPORT member keeps its item subject
`('nodes', 'members', 0)` untracked and exposes `('nodes', 'members')` as a separate
location. Its contributing source tokens remain available; replacing or reordering
members marks that container's locations as historical (`changed`). They are not
copied into the item's convenience `span`. Programmatic lists have no invented
source. Nested sequences use the first container whose path has no integer index.

Runner keeps each preflight diagnostic once when a recorded report subsequently
raises `ValidationError`. Distinct entries with equal values remain distinct,
and exceptions raised before their report is recorded still retain that report.

All contributing token spans are retained. A semantic diagnostic receives the
legacy `span` convenience field only when its primary location is current and
has exactly one token span. Explicit parser/native spans keep their own source
identity. A generated execution INP and the original edited model can therefore
have different, correctly labelled locations. Inspecting locations neither opens
source files nor renders the model. Resolution caches repeated subjects within
one validation pass and builds aggregate source indexes only when needed.

The first integration covers collection-local validation, missing references,
hydraulic node/link rules and shared-resource purpose/dimension rules. For
example, `regulator.requires_storage` points at the inlet reference and relates
the inlet node and routing option; invalid cross-section geometry retains all
of its declared tokens. Hydrology, snowpack and climate semantic checks also
provide explicit subjects. Rain-gage conflicts include both consumers and their
series; snow-transfer warnings include the recipient and relevant catchment
areas. Climate diagnostics retain the display ID `climate` while addressing the
actual `swmm:climate` singleton key `settings`. Missing settings identify the
omitted field and relate the declarations that require it. Monthly/series
aggregates retain all contributing tokens without inventing stable point IDs.
Quality, inflow, RDII, groundwater, LID, treatment and control semantic validators
also provide subjects. Coverage and LID limits relate the actual contributing
records; groundwater relates local overrides and inherited aquifer parameters.
RDII identifies the response positions selected for each effective month, with
the aggregate declarations as source context. Treatment equations and control
statements retain their composite keys; control diagnostics trace named
expressions through variables to their referenced objects. Indexed paths remain
untracked and include record/aggregate context rather than claiming persistent
tuple-item identity. Model OPTIONS run checks bind their own singleton and
related calendar/routing fields. The profile's `ResolvedOptions.report` remains
the legacy, unlocated report used by bootstrap snapshots; model validation adds
locations without silently changing that nested wire format.

Rejected settings and collection changes resolve diagnostics against the
candidate value before it is discarded. Their locations describe that attempted
value: `changed` spans are historical input, not an assertion that the valid old
value still in the model caused the error. The same rule applies to converted
candidates that fail before commit. Rollback restores records, origins and
revision while the exception retains candidate evidence. Explicit collection
edits retain deferred validation; a model transaction validates before rollback.
Deletion diagnostics include actual typed reference paths. Opaque INP guards
keep the unparsed line in `span` and the attempted target in `subject`; these
are separate sources. Unknown JSON constraints do not invent INP positions.

Unit conversion failures bind the owning record, known nested paths and shared
resource consumers. Control conversion follows named-expression references.
Custom unit callbacks may call `context.convert_value(child, path=('field',))`
with a relative typed path. The existing one-argument form still converts the
value, but failures use only the containing record as context because value
identity does not prove a field address. Validation errors from pollutant
conversion candidates retain their local diagnostic codes and paths rather
than being flattened into a generic conversion message.
File dependency guards identify the actual interface binding and affected model
records. File preflight attaches the declared `FileReference.path` to errors and
warnings, including byte limits, missing backend capabilities, inactive inputs
and output aliases. An external inspector's `span` describes the external data;
`locations` describes the INP declaration. A parser-local path is not treated as
a model field. Explicit inspector model subjects and existing evidence remain
intact, with the file declaration added as related evidence.

Path resolution/export rejections and missing staging resources retain model
locations. Capture and verification IO errors keep their original exception
type and operational failure classification; Runner adds a structured resource
diagnostic. A staged filename is a changed value, so its original INP token is
historical evidence. Shared captured inputs relate their declared consumers.
During checkpoint resume, new locations in the frozen execution input use
`checkpoint-input:<input SHA256>` rather than an invented filesystem origin.
Stored original diagnostics and explicitly named external sources are preserved.

Model JSON import diagnostics retain an unambiguous JSON path and a span in the
actual JSON text. Character positions account for escaping, Unicode, whitespace
and repeated values; missing members locate their existing parent container.
The document is indexed lazily once when a diagnostic needs it. Registered wire
names map to Python attributes explicitly. Unknown members identify their known
parent record or value, and unknown variants retain the supplied record key;
they do not acquire invented model fields. Record-key mismatches relate the
supplied and decoded identities. JSON positions remain separate from retained
INP `locations`, including fields promoted from older JSON and protected extras.

Successful INP decoder diagnostics can use the codec's verified source-row
binding to identify their record owners. A codec's unclaimed line, a different
codec's line, or a different source does not acquire an owner from its display
ID. Network, FILES and shared-resource parse failures also identify an explicit
attempted record when enough syntax is known. Those lines remain unclaimed;
an absent subject is not a claim of structured or native support. Unknown
syntax without a reliable identity remains source-only.

Other parser/runtime producers and remaining guard-specific cases still
require review; these additions are not a claim of complete diagnostic coverage.
An unbound diagnostic stays unbound rather than guessing from a same-named ID.
This is not completion of the full physical/topological validation matrix.

Result archives now write version 1.3 (compact, verified report evidence) and
read 1.0–1.2. Result-table JSON writes 1.2 and reads earlier 1.0/1.1 forms without
inventing locations. Table writers can explicitly request
1.1 only when no structured locations would be lost. Runner checkpoint envelopes
use codec 1.2 and still read 1.1. The inner state and bootstrap snapshot codecs
remain explicitly pinned to their existing format. Unknown fields/versions and
attempts to hide new metadata inside legacy envelopes are rejected.
