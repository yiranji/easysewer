# Testing and builds

Run commands from the repository root. The project uses a `src` layout; ordinary tests can run in an environment with the current package installed. Tests requiring native backends, optional dependencies or platform-specific behavior need the corresponding environment.

## Documentation, schemas and inventory

```console
python tools/audit_docs.py
python tools/build_result_schemas.py --check
python -m unittest discover -s tests -p test_support_matrix_audit.py -v
```

See the [support inventory](2.0-support-matrix.md) for inventory auditing and optional historical-evidence arguments. The `1.x` in Schema files denotes data-format versions used by current readers, writers and tests; these files must not be removed as obsolete software versions.

## Rebuildable delivery

The native branch separates source/pure packaging from per-platform native
builds. The already published PyPI `2.0.1` artifacts are unchanged; these commands
produce local development artifacts, not a new release. Run without `-O`, `-OO`
or `PYTHONOPTIMIZE`. Output directories must not already exist.

```console
python tools/build_release.py --source-only --output dist/rebuild
python tools/audit_docs.py --sdist dist/rebuild/native/easysewer-2.0.1.tar.gz
python tools/qualify_release.py --package dist/rebuild/installed-pure --pure --output build/release-pure-check
```

`--source-only` builds the audited source archive, extracts it, builds the pure
wheel from the extracted source and verifies the installed pure files. It does
not build a native wheel. The archive includes the published documents, native
recipes, tests, fixtures and tools needed by the subsequent platform jobs.
Use the extracted tree rather than an editable installation for final checks.

The native builder must run on the selected native 64-bit target. ARM builds
compile the standard solver and OUT reader from the public EPA SWMM 5.2.4
checkout pinned by `native/standard/source.json` and `native/output/source.json` (commit
`7952ca837988b1c32f791812eccc9fd64547e093`). Preparation checks the normalized
source hashes before applying the existing EasySewer patches. Neither a tag name
alone nor a changed upstream checkout is accepted. Keep upstream checkouts and
prepared/build outputs separate.

For example, on native Linux aarch64 inside the selected baseline build
environment, with the pinned EPA checkout already present at `/path/to/epa-swmm`:

```console
python dist/rebuild/extracted/easysewer-2.0.1/tools/build_native_wheel.py --platform linux-aarch64 --upstream /path/to/epa-swmm --compiler gcc --output dist/native
```

Linux aarch64 uses native `manylinux_2_28_aarch64` build tools and a separate
clean AlmaLinux 8 runtime gate. Linux builders need a GCC-compatible compiler
for compilation, `auditwheel`, `patchelf` and the compatible build-time OpenMP
runtime. The compiler and every bundled dependency must satisfy the baseline;
compiling on a newer host and merely renaming a wheel is not sufficient. The
final audit rejects unsupported ELF dependencies, architectures and symbol
versions.

Linux x86-64 instead preserves the existing compiled standard, OUT and
FlexiblePonding bytes before repair. Build on native x86-64 with the runtime
dependency supplied from the manylinux 2.28 environment:

```console
python dist/rebuild/extracted/easysewer-2.0.1/tools/build_native_wheel.py --platform linux-x86_64 --output dist/native
```

This route bundles `libgomp` without increasing the existing glibc 2.33 floor.
Audit final native bytes and dependencies for `GLIBC <= 2.33`, then execute the
wheel in a separate clean glibc 2.33 fixture. The final tag is generic
`linux_x86_64`, not a misleading manylinux 2.28 or 2.34 tag. The fixture checks
compatibility only; it is not a promise of security maintenance for an old Linux
distribution.

For Windows x86-64, the builder retains the checked-in, recorded standard, OUT
and experimental custom binaries and audits the final PE payload:

```console
python dist/rebuild/extracted/easysewer-2.0.1/tools/build_native_wheel.py --platform windows-x86_64 --output dist/native
```

For macOS arm64, build host-only LLVM OpenMP 18.1.8 from the exact commit and
source trees pinned in `native/openmp/source.json`. Build on native macOS 15
using a native arm64 Python, Apple Clang, CMake and `delocate`, with a macOS 14.0
deployment target for the solver, OUT reader and OpenMP runtime. The LLVM
checkout needs the pinned `openmp` and `cmake` trees; the build verifies their contents. Homebrew runtime bottles are
not the runtime provenance for the release wheel.

```console
python dist/rebuild/extracted/easysewer-2.0.1/native/openmp/build.py --source /path/to/llvm-project --build /path/to/libomp-build --prefix /path/to/libomp-prefix
python dist/rebuild/extracted/easysewer-2.0.1/tools/build_native_wheel.py --platform darwin-arm64 --upstream /path/to/epa-swmm --compiler clang --openmp-prefix /path/to/libomp-prefix --output dist/native
```

Both commands use the same extracted source tree. The OpenMP prefix is a build-time input; users of the final
wheel do not need that prefix or a separate Homebrew/OpenMP installation.
Native ARM builds reject a mismatched host process architecture. Rosetta, QEMU
and x86-64 cross-compilation are not substitutes for native ARM qualification.

`build_native_wheel.py` performs compilation or verified staging, creates an
intermediate platform wheel and invokes `tools/repair_native_wheel.py`. On
Linux this uses `auditwheel`; on macOS it uses `delocate`. The repair gate audits
all final native payloads and dependencies, verifies runtime baselines and
licenses, rewrites dependency-relative loader paths, then seals build records,
`runtime-manifest.json` and wheel `RECORD` with the final hashes. Install only the
result in `wheelhouse/`, never `raw/`. Any payload modification after sealing
requires another repair/audit and a new manifest, not a manually copied hash.

Native recipes are documented under [standard](../native/standard/README.md),
[OUT reader](../native/output/README.md),
[experimental custom](../native/flexible_ponding/README.md) and
[checkpoint](../native/checkpoint/README.md). The original standard numerical
policy remains `easysewer:standard:5.2.4:16`. Solver builds retain
`-fno-fast-math -ffp-contract=off`; adding a target does not change the equations
or authorize unsafe floating-point optimization. The private FlexiblePonding
source is not distributed or required to rebuild the public ARM core.

## Installed-package qualification

Install the repaired native wheel into a fresh directory. In a POSIX shell:

```console
python -m pip install --no-index --no-deps --no-compile --target installed-native dist/native/wheelhouse/*.whl
python dist/rebuild/extracted/easysewer-2.0.1/tools/qualify_release.py --package installed-native --core --output build/core-check
```

On Windows, pass the exact wheel filename instead of the wildcard. The qualifier
verifies that imports come from the installed package, not the source tree.
Choose one profile deliberately:

- `--core` requires the standard solver and native OUT reader. It selects
  platform-relevant core tests before execution, not optional-backend tests with
  tolerated skips. It includes native solve/output, resource, checkpoint and
  first-run checks. It is the required native platform gate.
- `--experimental` selects strict FlexiblePonding checks separately for the
  preserved x86-64 targets. It is not an ARM or core-readiness requirement and
  does not establish scientific validation of the experimental policy.
- `--pure` checks the solver-free package. `--archive` can additionally read a
  result archive produced by a successful native first-run example.
- Omitting a profile retains the previous all-backend native selection. It is
  intentionally not a synonym for `--core` and can fail where FlexiblePonding is
  absent.

Every selected test must pass. Empty selections, failures, skips, expected
failures and unexpected successes fail qualification; `--core` does not turn a
missing required native library into a skip. `--tests` replaces the selected
list with explicit test names; it does not filter experimental tests out of a
mixed module. Select core classes explicitly for targeted ARM rechecks.
Inspect `tests.log`, `tests.json` and `result.json` rather than counting a process
launch or an incomplete run as a pass.

```console
python tools/qualify_release.py --package installed-native --experimental --output build/experimental-check
python tools/qualify_release.py --package dist/rebuild/installed-pure --pure --archive build/core-check/first-run/archive-moved --output build/pure-archive-check
```

Run the first command only on a supported x86-64 package with FlexiblePonding.
Installed-package qualification and doctor establish only the tested runtime
and contract scope, not every physical parameter combination. Quick Start has
a separate verifier at `tools/qualify_quick_start.py`.

## Public continuous integration and evidence

The `Release validation` workflow is a validation-only gate with read-only
repository permissions; it does not publish a package. Native release evidence
must bind the exact commit, final wheel hash, OS/process architecture, Python
version, runtime baseline and selected qualification profile. The four native
targets are listed in [installation](2.0-installation.md). A matrix definition,
platform tag, static manifest or emulated run is not proof of a native pass.

Each platform must install its own final repaired wheel and run core qualification
on its actual native OS/architecture. Runtime gates include a clean glibc 2.33
x86-64 fixture, clean AlmaLinux 8 aarch64 and native macOS 14 baseline execution.
The continuing macOS matrix uses 15 and 26; the time-limited macOS 14 baseline
runner and its retained evidence must not be confused with the build host or
ongoing matrix. A deployment flag alone does not prove minimum-OS execution.
A rebuilt wheel cannot inherit a different wheel's baseline execution record;
when the macOS 14 runner is unavailable, a fresh minimum-OS claim needs another
actual native macOS 14 environment. The x86-64 targets additionally retain
strict experimental checks. The pure profile remains separate and must still
read the native first-run archive. Retain doctor JSON, compiler/repair logs,
dependency audits and test results, including failed attempts. Claims about a
completed target pass require that target's successful run evidence.

Windows compatibility gates require an actual Windows runner and, for alias
checks, a volume providing existing ASCII short-name aliases. An unavailable
alias fails the selected compatibility gate instead of silently skipping it.
Windows file-sharing and directory-handle cases retain separate targeted
qualification. Core checks must select the standard family; the experimental
family is qualified separately. These tests do not imply a fix for the
intermittent [Windows directory publication issue](2.0-known-issues.md).

The shipped source-archive extractor validates paths and member types before
creating a fresh destination. It rejects links and special files and supports
Python 3.10.11, which predates `tarfile`'s data filter. Runtime checks use the tests,
tools and examples shipped in that source archive. Isolated numerical oracles
must import the same installed package as their calling tests.

Run the release-tool regressions locally with:

```console
python -m unittest discover -s tests -p test_release_tools.py -v
python -m unittest discover -s tests -p test_native_toolchain.py -v
python -m unittest discover -s tests -p test_native_wheel_repair.py -v
```

## Current-format and Horton regression contracts

Routine tests use the current package and its bundled backends. They do not
require preserved candidate packages or previous native libraries. The directory
suite checks valid round trips, member/topology integrity, deterministic
directory-free archive and file-only checkpoint serialization, and rejection of
unsupported or synthetically downgraded
format envelopes. Tampered checkpoint commits and context hashes are recomputed
when testing format rejection, so a checksum error cannot conceal a missing
format check. These are current-reader contract tests, not evidence of how an
unavailable historical reader behaved.

Run the directory group on Linux or macOS:

```console
PYTHONPATH=src:tests python -m unittest -v test_directory_artifact_v2 test_directory_checkpoint_v2 test_directory_group_integration_v2 test_hardlink_directory_v2 test_mixed_resource_graph_v2 test_mutable_directory_v2 test_optional_mutable_directory_v2 test_output_directory_checkpoint_v2
```

On Windows PowerShell, set `$env:PYTHONPATH = 'src;tests'` before the same
`python -m unittest` command.

The Horton integration suites exercise both current backend families across all
six flow units. They combine repeat-run output checks with analytical fixture
limits, fresh-process checkpoint continuation and cache reuse. Synthetic engine
identity mismatches test revision refusal before solver open or output replacement;
they do not stand in for actual previous solver executions.

Select standard classes explicitly for the core gate, including ARM:

```console
python tools/qualify_release.py --package installed-native --core --output build/horton-core-check --tests test_native_horton_integration_v2.HortonIntegrationTests test_native_horton_outfall_v2.HortonIntegrationTests
```

Select `ExperimentalHortonIntegrationTests` in both modules for the separate
x86-64 experimental gate. Selecting each whole module retains its historical
all-family behavior and therefore requires both backends. Any selected skip or
other nonpassing test fails the gate.

The replacements remove 13 tests' historical-asset dependencies, along with the
unused historical fixture locator and its selection-only tests. They establish
current behavior only. Byte-for-byte compatibility with an unavailable old
writer, version-specific old-reader refusal, and old-versus-new numerical
comparisons remain unverified historical evidence, not known current defects.

## Publication is a separate release decision

PyPI `2.0.1` is already a final published release. The branch does not replace
those immutable distribution files and does not publish a new version. Do not
upload a branch wheel as though it were the already released universal native
wheel. The pure profile is a separate local artifact, not another native target.

Before a future publication, choose an unpublished release version and review
the publisher's artifact contract for the complete platform wheel set and source
archive. Require successful native qualification for that exact commit and each
published platform, inspect dependency/license evidence, and check distribution
metadata. Upload only final repaired artifacts already verified by that run;
do not rebuild them during publishing. A version string or branch name is not
proof of publication or qualification.

The historical `Publish to PyPI` workflow was designed for the older native-wheel
artifact layout. Do not assume it can publish this branch's multi-platform set
without reviewing its checks and artifact selection. A configured Trusted
Publisher does not authorize a release by itself. After any separately authorized
future release, verify the PyPI files and a fresh install on each supported target.

## Interpreting evidence

Current verification after removal of all 1.x compatibility code is recorded in `build/remove-v1-compat-20260930/verification.json`. Earlier API-removal records are historical snapshots. Documentation cleanup records are under `build/docs-cleanup-20260930/`, and English-language checks are under `build/docs-english-20260930/`. These are local build records and are not bundled in releases.

Each record applies only to its bound source, package and environment. Repeated executions must not be summed as independent tests, and successful retries do not erase initial failures. See the [development archive](development-archive.md) for historical material and [known issues](2.0-known-issues.md) for unfinished work.
