# Testing and builds

Run commands from the repository root. The project uses a `src` layout; ordinary tests can run in an environment with the current package installed. Tests requiring native backends, optional dependencies or platform-specific behavior need the corresponding environment.

## Documentation, schemas and inventory

```console
python tools/audit_docs.py
python tools/build_result_schemas.py --check
python -m unittest discover -s tests -p test_support_matrix_audit.py -v
```

See the [support inventory](2.0-support-matrix.md) for inventory auditing and optional historical-evidence arguments. The `1.x` in Schema files denotes data-format versions used by current readers, writers and tests; these files must not be removed as obsolete software versions.

## Rebuildable delivery

```console
python tools/build_release.py --output dist/rebuild
python tools/audit_docs.py --sdist dist/rebuild/native/easysewer-2.0.0.tar.gz
python tools/qualify_release.py --package dist/rebuild/installed-native --output build/release-native-check
python tools/qualify_release.py --package dist/rebuild/installed-pure --pure --output build/release-pure-check
```

Build and qualification output directories must not already exist. The builder copies documents from the explicit publication list, creates a source distribution, rebuilds native and pure packages from it, verifies tests/fixtures and package members, then installs the packages and checks every file. Native build recipes are documented under [standard](../native/standard/README.md), [custom](../native/flexible_ponding/README.md) and [checkpoint](../native/checkpoint/README.md).

Installed-package qualification covers APIs, editing, scenarios, project metadata, results and the first-run example. It does not replace verification of every platform or physical parameter combination. Run `qualify_release.py --help` for targeted-test and archive-reading options. Quick Start has a separate verifier at `tools/qualify_quick_start.py`.

Release validation must run without `-O`, `-OO` or `PYTHONOPTIMIZE`: the builder,
auditors and first-run example use assertions as integrity checks. The build and
qualification commands reject optimized interpreters before creating output.
Qualification also rejects empty selections, failed, skipped and expected-failure tests;
inspect `tests.log` and `tests.json` when a check fails.

## Public continuous integration

The `Release validation` GitHub Actions workflow runs on pushes, pull requests
and manual dispatch. It audits documentation and generated result schemas,
regression-tests the release gates, then uses Python 3.13 to rebuild both wheel
profiles from a source archive and check their distribution metadata.

The same wheels are installed into separate directories and qualified on
Windows and Linux x86_64 with Python 3.10, 3.11, 3.12, 3.13 and 3.14. Runtime jobs
use the tests, tools and example shipped in the source archive; they do not need
a repository checkout or a source/editable package install. The pure profile
also reads the archive produced by the native first-run example. Each cell runs
the targeted installed-package qualification suite, not the entire native test
inventory. This does not cover macOS, ARM, Pyodide execution or native rebuilds.

Windows native qualification also requires a temporary volume with existing ASCII
short-name aliases. It checks that the worker retains the compatible spelling of
the same directory, both backends produce identical OUT bytes under Unicode
destinations, explicit Unicode scratch stays in place and is cleaned after
cancellation, and moved Unicode checkpoints can repeatedly restore directory
inputs, LID outputs and custom traces. A missing alias fails this compatibility
gate; it does not silently skip it. Separate tests preserve the original failure
and previous outputs when an alias is unavailable, and reject aliases for a
different directory. The runtime still supports only the bounded behavior in
[known issues](2.0-known-issues.md).

Isolated numerical-oracle subprocesses used by installed-package qualification
must import the same installed package as the calling test. The climate-resource
oracle checks that identity explicitly instead of selecting the source archive's
`src` tree.

The artifact includes a standalone source-archive extractor so runtime jobs can
start on Windows Python 3.10.11, which predates `tarfile`'s data filter. It
validates all member paths and types before creating a fresh destination,
rejects links and special files, and uses the data filter where available.
On older interpreters it copies only validated regular-file bytes without
restoring archive ownership or permissions.

Native qualification exercises directory publication, moved checkpoints and
repeated output-directory restore using both packaged standard and custom
backends. These checks run in the Windows and Linux CI cells; the pure suite
remains unchanged. This coverage does not establish that the intermittent
[Windows directory publication failure](2.0-known-issues.md) has been fixed.

A separate Windows-only CI step selects eight existing file-handling tests:
four journal-reader/replacement cases, one UTF-16 filename case and three
directory-handle publication/recovery cases. It uses the installed native
package and retains `checks/windows-files/tests.log` and `tests.json`, including
failure evidence. Any skipped or nonpassing selected test fails this gate.
The default native and pure selections remain unchanged. These checks require
an actual Windows runner; invoking their explicit selection on Linux produces
eight skips and fails qualification, rather than establishing a Windows pass.

The workflow retains build and test evidence, including logs from failed checks.
It has read-only repository permissions and does not publish a package. Native
and pure wheels have identical filenames, so artifact paths keep the profiles
separate. To run the release-tool regression tests locally:

```console
python -m unittest discover -s tests -p test_release_tools.py -v
```

## Optional historical-reader fixtures

Six directory-format compatibility checks need preserved installed packages
named `candidate-v12`, `candidate-v14`, `candidate-v16`, `candidate-v20`,
`candidate-v22` and `candidate-v36`. Each package must have
`HISTORY_ROOT/candidate-vN/easysewer/__init__.py`. Set
`EASYSEWER_DIRECTORY_HISTORY_ROOT` to choose a fixture root explicitly; otherwise
the tests look under the repository root.

Missing default fixtures produce six individually named unittest skips.
Current-format assertions run independently and must still pass. An explicitly
configured empty or missing root, a missing requested candidate, or a present
malformed fixture is an error rather than a skip. Historical subprocesses use
isolated Python (`-I -B`) and verify which package was imported.

The public workflow runs these checks separately from the strict, no-skips
installed-package qualification. A skip does not validate an old reader: supply
the actual preserved packages to substantiate version-specific rejection. The
fixture-helper regression tests validate fixture selection, not historical
reader behavior. To run this group on Linux or macOS:

```console
PYTHONPATH=src:tests python -m unittest -v test_directory_history_fixture test_directory_group_integration_v2 test_hardlink_directory_v2 test_mixed_resource_graph_v2 test_mutable_directory_v2 test_optional_mutable_directory_v2 test_output_directory_checkpoint_v2
```

On Windows PowerShell, set `$env:PYTHONPATH = 'src;tests'` before the same
`python -m unittest` command.

## Build and publish to PyPI

Build from the committed `master` checkout using Python 3.13, the interpreter
used for the current Windows release checks. The installed package supports
Python 3.10 or later. Use a fresh output directory for each build and check run.

```console
git switch master
git pull --ff-only github master
python -m pip install --upgrade "setuptools>=77.0.3" wheel twine
python tools/build_release.py --output dist/pypi-2.0.0
python tools/qualify_release.py --package dist/pypi-2.0.0/installed-native --output build/pypi-2.0.0-native-check
python tools/qualify_release.py --package dist/pypi-2.0.0/installed-pure --pure --output build/pypi-2.0.0-pure-check
python -m twine check --strict dist/pypi-2.0.0/native/easysewer-2.0.0-py3-none-any.whl dist/pypi-2.0.0/native/easysewer-2.0.0.tar.gz
```

Continue only if every command succeeds. The builder audits the documentation
and source archive, builds both wheel profiles, and verifies the installed files.
The release upload consists of exactly these two files from `native/`:

- `easysewer-2.0.0-py3-none-any.whl`
- `easysewer-2.0.0.tar.gz`

The pure wheel has the same filename as the native wheel. Keep it as a local
artifact; do not upload it as another variant or upload the entire output tree.
Publish manually using your PyPI credentials:

```console
python -m twine upload dist/pypi-2.0.0/native/easysewer-2.0.0-py3-none-any.whl dist/pypi-2.0.0/native/easysewer-2.0.0.tar.gz
```

Version `2.0.0` is a final release, with no `.dev`, alpha, beta or release-candidate
suffix. After publication, fresh installations select it when it is the latest
compatible final release; existing installations require `--upgrade` to update.
The Git branch name does not determine PyPI release status.

After publication, check installation in a fresh environment:

```console
python -m venv build/pypi-2.0.0-install-check
build/pypi-2.0.0-install-check/Scripts/python.exe -m pip install --index-url https://pypi.org/simple easysewer==2.0.0
build/pypi-2.0.0-install-check/Scripts/python.exe -c "from importlib.metadata import version; from easysewer import Model; print(version('easysewer')); print(Model())"
```

These last commands use Windows paths. On Linux, use the environment's
`bin/python` executable instead of `Scripts/python.exe`.

## Interpreting evidence

Current verification after removal of all 1.x compatibility code is recorded in `build/remove-v1-compat-20260930/verification.json`. Earlier API-removal records are historical snapshots. Documentation cleanup records are under `build/docs-cleanup-20260930/`, and English-language checks are under `build/docs-english-20260930/`. These are local build records and are not bundled in releases.

Each record applies only to its bound source, package and environment. Repeated executions must not be summed as independent tests, and successful retries do not erase initial failures. See the [development archive](development-archive.md) for historical material and [known issues](2.0-known-issues.md) for unfinished work.
