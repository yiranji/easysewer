# 2.0 backend and session

The standard backend runs one SWMM project in one hidden Python worker process. The parent does not load a SWMM library. Importing easysewer.runtime does not discover libraries or create processes.

```python
from pathlib import Path
from easysewer.runtime import StandardBackend

backend = StandardBackend()
capability = backend.probe()  # actual load and version call, in a disposable worker
if not capability.available:
    raise RuntimeError(capability.reason)

directory = Path("simulation").resolve()  # must already exist
with backend.session(working_directory=directory, call_timeout=30) as session:
    identities = session.open("model.inp", "model.rpt", "model.out")
    session.start(save_results=True)
    while not session.step(max_steps=100).finished:
        pass
    continuity = session.end()
    session.report()
```

This is an explicit low-level session for trusted, validated input.
[Runner](2.0-runner.md) connects Model validation, RunConfig, captured file
preflight, ownership, immutable snapshots and structured RunResult. A successful native
return does not certify hydraulic accuracy, acceptable continuity error, or
cache reuse suitability. `MassBalance` exposes the actual percentages; it does
not silently clamp them or classify a result by an arbitrary threshold.

## Capability and provenance

`BackendInfo` is immutable and records the loaded absolute path, SHA-256,
reported engine version, platform, architecture, ABI, profile and isolation.
The packaged standard binaries are pinned by their byte hashes. A digest is
checked before loading and again after loading; changed bytes fail. Version
52004 and the required C symbols must be present. The
[standard build manifest and recipes](../native/standard/README.md) additionally
record the fixed EPA source, EasySewer corrections, compiler options and final
hashes. Current packaged bytes report `numerical_policy=easysewer:standard:5.2.4:16`
and capability `easysewer:standard-fixes:16`; their NWS rainfall arithmetic is
explicitly `reference` in `output_semantics`. These records are evidence rather
than signatures or a guarantee of all-platform physical equivalence.

Revision 13 adds `easysewer:checkpoint:2` and the six corrections recorded in
the [checkpoint build recipe](../native/checkpoint/README.md): event/rule clocks,
inactive routing clocks, parabolic storage exfiltration, sag inlet road sides,
groundwater conductivity and snow initialization. Explicitly selected known
revision 12 bytes retain their revision 12 identity and I/O capabilities without
claiming checkpoint support. Unknown hashes cannot acquire these correction
claims through a caller-provided expected digest or a native version symbol.
Checkpoint archives bind exact engine bytes; changing a library requires a new
execution rather than an implicit checkpoint migration.

Revision 2 includes [checked RAIN I/O](2.0-native-io.md) as well as HOTSTART
and lifecycle corrections. A native RAIN read/write failure reports 322/324,
including failures during stepping or close; the session and Runner retain that
failure and do not publish an incomplete produced cache.
Revision 3 also adds [complete RUNOFF I/O checks](2.0-native-io.md), read-only
USE and checked write error 326. A failed RUNOFF start stops subsequent
initialization, preserving the primary error and later HOTSTART outputs.
Revision 4 adds the separately recorded `easysewer:runoff-physics:1`
[replay corrections](2.0-runoff-replay.md) for evaporation and groundwater
dimensions/state. It does not change the RUNOFF binary format.
Revision 5 adds `easysewer:runoff-rain-clock:1`: rain reports and accumulated
rain controls advance by the consumer's actual clock during USE RUNOFF,
independently of cached frame lengths. `output_semantics` records it under
`swmm:runoff-rain-clock`. Unknown library hashes receive no such capability.
Revision 6 adds `easysewer:rdii-io:1` for [RDII frame and I/O checks](2.0-native-io.md),
bounded generation arithmetic and explicit used-hydrograph rain-gage binding.
This capability also requires a known library hash.

Revision 7 adds `easysewer:routing-io:1` for [routing frames and checked I/O](2.0-native-io.md),
including pollutant-bearing files consumed by zero-pollutant targets. Runner
passes the selected backend's capabilities to file preflight. Runtime capability
requirements accept exact versioned IDs and survive RunConfig JSON round trips.

Revision 8 adds `easysewer:solver-output-io:1` for
[solver OUT writes, report reads and completion](2.0-native-io.md).
Write/flush/close failures propagate through the worker; Runner preserves an
existing publication when completion fails. This capability is separate from
the SMO output-reader library's revision and also requires known binary bytes.

An explicit `StandardBackend(library=absolute_path, expected_sha256=digest)`
selects a user-provided library. Without a digest its actual hash is recorded,
but its bytes are not pinned. Bytes outside the known build set report
`numerical_policy=user-library:unverified`; a supplied hash or matching version
does not establish source or compiler provenance. Native libraries are trusted executable code;
the worker is a lifecycle boundary, not a security sandbox. Only the standard
SWMM 5.2.4 API is advertised. Selecting the FlexiblePonding DLL through this
interface does not apply the FlexiblePonding algorithm or advertise its policy.

`probe()` performs a real load and version call, then closes and reaps the
worker. Absence, an unloadable DLL, wrong version, digest mismatch, unsupported
runtime, or worker launch failure yields `available=False` with a reason.
It does not claim to validate every function's numerical behavior.
The legacy `get_native_capabilities()` retains its file-existence semantics.

The pure Python packaging profile includes the protocol and discovery facade,
but excludes executable workers and native libraries. Normal Python is required
for execution. Frozen applications, Emscripten and WASI have no supported worker
launcher yet. Actual Windows x86_64 and Ubuntu 24.04/WSL x86_64 tests are recorded
in the development plan; a platform hash entry alone is not execution evidence,
and other deployment/runtime combinations still need qualification.

## Lifecycle and errors

The normal sequence is `LOADED → OPEN → STARTED → FINISHED → ENDED → REPORTED →
CLOSED`. `end()` may also stop an active simulation early; `report()` is an
explicit, optional operation after `end()`. Repeated start/end/report, stepping
after completion, and calling operations out of order raise `SessionStateError`.
`close()` is idempotent from any public state. It attempts native end after a
partial start and native close after a partial open, then waits for process exit.
No output is deleted and no report is generated implicitly by close.

Every native return code is checked, including mass-balance access. A
`SessionError` contains `failure` (stage, native code and message), separate
`cleanup` failures, a bounded stderr tail and the worker return code. The worker
sends a primary failure before beginning cleanup, then streams cleanup failures.
Thus a blocked or crashing cleanup cannot replace an already reported primary
cause with a transport timeout. User exceptions escaping a `with` body remain
the primary Python exception; cleanup remains available on the session.

`call_timeout` is a finite positive number of seconds per RPC, including an
entire step batch. Cleanup has a separate bounded wait of at most five seconds.
Runner additionally enforces RunConfig's whole-run wall-clock limit. A cancellation event
with `is_set()`, or `session.cancel()` from another thread, is checked during an
in-flight call and before the next call. Cancellation/timeout kills and reaps the
worker, even if native code or a request-pipe write is blocked. Calls on a shared
session are serialized. Separate sessions use independent global native state.

Workers use a versioned JSON-lines allowlist without pickle or dynamic command
execution. Native stdout is redirected away from the response channel. Frames
have an explicit 16 MiB limit, and retained stderr is at most 64 KiB of bytes.
The worker exits on parent stdin EOF even while a native call is blocked.
Explicit close/context management is required; a finalizer only provides a last
resort to reap an abandoned worker and never produces a final report.

Process exit releases leaked native resources through the operating system. It
does not repair C allocation bugs. On the bundled Windows binary, normal climate
runs without catchments and failed climate opens now permit immediate deletion
of their weather files after the session ends. A missing climate month fails
during **open**; a complete final record without a newline is accepted by the
[qualified climate reader](2.0-native-io.md). A missing USE
HOTSTART fixture separately proves partial **start** cleanup, with error 331
preserved when end returns the same error again.

## Identity, files and remaining integration

`EngineObjects` contains names queried through the loaded engine's
`getCount/getName/getIndex` API. Lookups use SWMM's ASCII case rule and verify
reverse indices. `open(expected=...)` compares expected identity sets before
start, while engine order remains authoritative. This API exposes gages,
subcatchments, nodes and links; it does not invent pollutant indices.
The engine's complete object list differs from selected OUT identities, which
are read independently by Runner's OUT metadata reader.

`working_directory` must be an existing absolute directory. Only the worker
changes cwd; relative INP/RPT/OUT paths are resolved against that directory.
Open rejects missing input, file aliases (including existing hard links), missing
output directories and existing outputs unless `overwrite=True` is explicit.
These are low-level checks, not a concurrent reservation or complete external
file audit. Native INP can open or write referenced files during open itself.
Low-level session callers own all such paths. Runner applies consumer inventory,
captured-input checks, reservations and failure retention before opening.
The session passes relative names for files below its working directory;
Runner uses short ASCII relative names for execution and captured resources,
including under Windows Unicode directories. Direct external paths still use
the native library's file-name encoding behavior.

Runner applies RunConfig, progress callbacks, whole-run deadlines, REPORT policy
and observed cache producer/consumer provenance. [Production-condition evidence](2.0-cache-conditions.md)
records reuse comparisons and their origin; its supported policies define the
comparison scope. [OUT queries](2.0-output.md), [RPT and LID report queries](2.0-report.md)
and [result archives](2.0-result-archive.md) have public interfaces. Remaining exhaustive review is tracked in [known issues](2.0-known-issues.md).
[FlexiblePonding](2.0-flexible-ponding.md) binds threshold units and
actual IDs, with discrete water/quality accounting and adjusted native statistics. Current delivery scope is recorded in [delivery scope](2.0-delivery.md).

Native lifecycle semantics were checked against the official
[SWMM 5.2.4 implementation](https://github.com/USEPA/Stormwater-Management-Model/blob/v5.2.4/src/solver/swmm5.c)
and [C API header](https://github.com/USEPA/Stormwater-Management-Model/blob/v5.2.4/src/solver/include/swmm5.h),
with independent execution of the packaged artifact.
