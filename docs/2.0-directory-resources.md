# Directory resources (2.0 development)

A registered model codec can declare `FileUse(kind="directory", access=...)`
with a namespaced format. `Runner` requires an explicit `DirectoryAdapter` for
each active regular-directory format. An adapter validates content; the
framework captures files, records evidence and controls publication. Registering
an adapter does not teach a codec or native engine how to consume that format.
The codec must also declare each native file consumer and write its rebound path.

```python
from easysewer.runtime import DirectoryAdapter, DirectoryLimits, Runner
from easysewer.io.interface_inspection import InterfaceInspection

def inspect_bundle(root, *, manifest, use, model, encoding, source):
    # Validate this format here; report invalid content through the report field.
    # root is a captured execution tree during Runner preflight.
    return InterfaceInspection(format=use.format, status="validated")

runner = Runner(directory_adapters={
    "acme:rain-bundle": DirectoryAdapter(
        inspector=inspect_bundle,
        limits=DirectoryLimits(total_bytes=32 * 1024**2, entries=10000, depth=16),
    ),
})
```

This snippet registers the adapter shape only; replace the placeholder validator
with real format checks and supply a model codec declaring this format before
running a model. `check_files(..., directory_adapters=...)` also accepts the
registry and performs read-only preflight. Existence alone is not full format
inspection. Explicit inspector exceptions retain their original identity/chain;
return an inspection report for a data validation failure.

## Access and shared consumers

- `read` uses a verified private capture. The caller's source is never modified.
- `read_write` creates a writable execution copy and preserves independent
  initial evidence. Native changes to the copy do not alter the caller's tree.
- `write` creates a private output tree and publishes it only after successful
  verification. Empty directories and declared child outputs are represented.
- Inactive resources do not require access to their original location. Missing
  optional resources retain explicit absence; required missing resources fail.

Shared sources, nested declarations, hardlinked regular files and mixed file/tree
views are captured as groups when needed. Each consumer retains its identity
and path within that group. Initial evidence cannot alias a writable execution
tree. Internal hardlinks are preserved through capture and restoration; original
external files are never linked into a writable private tree. Symbolic links,
reparse points, special files and nonportable/case-colliding names are rejected.

## Budgets and interruption

`DirectoryLimits` defaults to 256 MiB, 100000 entries and depth 64. Runner clips
adapter limits to its global directory limits; file inspection/capture byte
limits also apply. The budget covers the declared tree, not just the file the
engine happens to read. Growth, truncation, newly added members and short writes
fail instead of producing a successful partial capture. These byte/count/depth
budgets do not cap total Python memory, filesystem allocation or cleanup time.

Built-in scans, capture, verification, collection and publication check the run
cancellation event and wall deadline. Mandatory rollback, worker shutdown and
full retained-evidence hashing may continue after cancellation. A single system
call or arbitrary inspector code cannot be forcibly interrupted.

## Output ownership and recovery

Existing directory outputs require `overwrite=True`. Replacement publishes the
whole declared tree, including removal of old members absent from the new tree;
it does not merge with the old contents. The transaction records and rechecks
the old tree, retains a private backup and restores it on pre-commit failure.
External changes produce a conflict and preserve evidence for explicit recovery.
Successful commit followed by a cancellation request remains successful.

Crash recovery verifies recorded identity and content before acting. Cleanup
authorization is journaled before removal and supports verified partial retry.
New directory transactions use recovery log versions 7/8; file-only versions 5/6
remain readable. Older readers reject unsupported logs. This is process-crash
recovery under the stated filesystem assumptions, not a power-loss or hostile
concurrent-writer guarantee.

## Archives and checkpoints

`RunResult` exposes directory and directory-group artifacts in addition to file
artifacts. A writable input has both initial and current evidence. Saving a
failed run preserves only returned artifacts; removed workspace bytes cannot be
recovered by saving later. Result archives can be moved independently of their
original source trees. See [result archive versions](2.0-result-archive.md).

Checkpoint container and snapshot codec versions are selected together:

| Inner checkpoint | Snapshot codec | Added representation |
| --- | --- | --- |
| 1.0 | 1.1 | Existing file-only state |
| 1.1 | 1.4 | Directory input evidence |
| 1.2 | 1.5 | Mutable directory state |
| 1.3 | 1.6 | Explicit optional absence |
| 1.4 | 1.7 | Internal hardlinks |
| 1.5 | 1.8 | Shared directory groups |
| 1.6 | 1.9 | Mixed file/directory views |
| 1.7 | Selected by `base_schema_version` | Output directory states and native stream bindings |
| 1.8 | Selected by `base_schema_version` | Output members owned by mutable input directories |

Versions 1.7 and 1.8 wrap a base checkpoint from 1.0 through 1.6. The explicit
`base_schema_version` retains that base format's snapshot codec selection; the
wrapper does not introduce a new snapshot codec. Output directory manifests use
the result codec 1.9, and native stream bindings retain their declared member
paths and ownership during restoration.

The outer Runner context stays schema 1.0/codec 1.2. Original extension record
identity and ordering must be reconstructible by the explicit schema, and the
reconstructed execution INP must match exactly. Re-importing INP to assign new
identities is not a substitute. Native continuation still requires matching
platform, engine library bytes, model, configuration and captured resources.

The pure Python profile includes the data contracts and archive/inspection
helpers. It does not include native execution workers or provide a WASM solver.
Host-only pure-profile validation does not replace actual browser/Pyodide
acceptance. Final API freeze, full-scale performance and release qualification
remain separate gates for this development snapshot.
