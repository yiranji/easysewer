# 2.0 delivery scope

The current local version is `2.0.1`. This delivery prioritizes the main modeling, execution and result-reading workflows. Follow-up work is listed in [known issues](2.0-known-issues.md).

## Native platform branch (not yet published)

This branch adds a native standard-SWMM and OUT-reader contract for
`windows-x86_64`, `linux-x86_64`, `linux-aarch64` and `darwin-arm64`. Each final
wheel is platform-specific, includes its non-system native dependencies and
records final repaired bytes in a runtime manifest. The source and numerical
policy remain pinned to EPA SWMM 5.2.4 with EasySewer standard revision 16;
adding an architecture does not authorize fast-math or an equation change.

`python -m easysewer doctor` and `easysewer doctor` check files and isolated
load/ABI readiness without solving, repairing or auto-installing anything.
`--json` produces structured evidence; `--smoke-test` explicitly adds a minimal
temporary solve and output read. Availability is not numerical or scientific
validity. See [installation](2.0-installation.md) for exit codes and boundaries.

FlexiblePonding is an experimental, scientifically unvalidated replaceable-backend
example. Its existing x86-64 behavior is preserved, it is optional on ARM and it
is not a core release gate. An unavailable requested backend fails explicitly.
There is no new claim for Intel macOS, Windows ARM, ARM32, musl, `universal2`,
emulation qualification or cross-architecture checkpoint compatibility.

The published PyPI `2.0.1` files are unchanged. Branch artifacts and configured
CI targets do not establish a completed platform pass or a new release.

## Published 2.0.1 release notes

- Improve native backend compatibility diagnostics, including Linux runtime
  requirements and Windows Python ABI checks.
- Preserve Windows native workspace paths using verified aliases where the
  filesystem provides them, with explicit diagnostics when a compatible path is
  unavailable.
- Harden release validation against optimized interpreters, skipped tests and
  incomplete source archives, and support source extraction on Python 3.10.
- Qualify the built native and pure packages on Windows/Linux x86-64 with Python
  3.10–3.14, including current directory/checkpoint and Horton regression checks.
- Replace tests that required unavailable historical binaries with reproducible
  current-format and numerical contracts. Historical cross-version evidence and
  the remaining issues in [known issues](2.0-known-issues.md) remain out of scope.

## Included capabilities

- `from easysewer import Model` uses the 2.0 model. The old ModelAPI, LegacyModel, UDM, object containers and JSON tools have been removed.
- Structured modeling and editing, INP/JSON round-trips, reference updates, transactions.
- Standard SWMM execution, optional experimental FlexiblePonding, OUT/RPT reading, result archives and checkpoint recovery.
- Platform-specific native builds for the target contract above, a pure Python package and a rebuildable source distribution. The pure package supports modeling, conversion and result reading; simulation requires a native backend.
- Standard revision 16 and custom native I/O revision 14. Importing top-level Model does not load native libraries. Capabilities are established by runtime probing and packaged digests.

## Usage and maintenance

Build tools write to the explicit output directory you choose. A local artifact does not imply publication to a package index or remote release. See [installation](2.0-installation.md) and the [first runnable example](2.0-first-run.md).

Testing and rebuild instructions are in [testing](2.0-testing.md). The support inventory, historical acceptance for particular snapshots and current installed-package checks have different scopes and do not substitute for one another. Blocked normal runs, incorrect results and data loss still require fixes.

EasySewer 2.0 has no compatibility or migration layer for 1.x APIs, rain/calc JSON, object snapshots or business formats. The `compat` package and its conversion workflows have been removed. Standard SWMM INP reading and writing remain core 2.0 features. The `1.x` in Schema filenames denotes data-format versions, independently of the package version.
