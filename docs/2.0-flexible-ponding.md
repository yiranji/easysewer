# Candidate FlexiblePonding backend

`easysewer.runtime.FlexiblePondingBackend` runs the custom engine in the same
isolated, cancellable process infrastructure as the standard backend. It requires
custom ABI 201 and active DYNWAVE routing with `ALLOW_PONDING YES`. StandardBackend
rejects a custom library, and FlexiblePondingBackend rejects missing/custom ABI
versions explicitly. Importing either facade does not load native code.

This is a candidate execution implementation. Water and mixed pollutant removal
use discrete end-of-step quantities, and native statistics observe the adjusted
state. Analytical closed-node balances and standard-engine overflow comparisons
test those contracts independently of a second call to the same custom ABI.

```python
from easysewer.model import Model, FileReference
from easysewer.io.json import JsonDocument
from easysewer.runtime import RunConfig, FlexiblePondingPolicy

model = Model.from_inp("network.inp")
policy = FlexiblePondingPolicy(
    external_flooding_ratio=0.5,
    depth_threshold_m=0.3,
    flow_threshold_cms=0.1,
)
result = model.run(RunConfig(
    backend="easysewer:flexible-ponding",
    output_directory=FileReference(path="runs/ponding", direction="output"),
    extensions=JsonDocument.from_data({
        "easysewer:flexible-ponding": policy.to_json_document().data,
    }),
))
result.raise_for_status()
totals = result.backend_results.data
trace = result.artifact("easysewer:flexible-ponding-steps")
```

## Numerical policy and units

The versioned policy is `easysewer:flexible-ponding:incremental-volume:2`.
Thresholds are explicitly meters and cubic meters per second; the backend
converts them to the snapshot's engine units. The fraction accepts both 0 and 1.
Nonfinite numbers, booleans used as numbers, unknown fields and unknown policy
versions are rejected. The policy JSON shape is defined in
[flexible-ponding-policy-1.0.schema.json](flexible-ponding-policy-1.0.schema.json).
Its schema version and the numerical policy version serve different purposes.

The algorithm selects Junction/Divider nodes with positive ponded area. It reads
initial ponding depth and volume **after** native start, including HOTSTART state.
Every route step reads the actual new state and refreshes history even when no
removal takes place. Removal requires positive depth and volume growth, ponding
depth above the depth threshold, and positive overflow above the flow threshold.

With ponding depth `h`, volume `V`, previous values `h0/V0`, native volume per
unit depth `a`, overflow `q`, elapsed seconds `dt`, fraction `r`, and conversion
factor `k` from native volume/second to native flow units:

```text
increment = min(V - V0, a * (h - h0), a * h, V)
removed   = min(r * increment, q / k * dt)
external  = removed / dt * k
h' = h - removed/a; V' = V - removed; q' = q - external
```

The bounds prevent removal of a stale accumulated increase, below-ground storage
or more positive overflow than is available this step. SWMM's rounded unit
constants require separate conversions for area, depth, volume and flow.
Multiplying the model's area by depth without those factors is incorrect in SI;
interpreting GPM/MGD/LPS/MLD as native volume per second is also incorrect.

Each step checks `execRouting` before any state change, uses the independent
native routing interval for `dt`, checks void setters by reading back state, and
checks `saveResults` after applying all adjustments. The clock must advance within
the simulation window. Native errors and invalid state fail the run; they are
not silently skipped. The native finalization call is required exactly once per
routing step, including when a low-level Session uses `save_results=False`.
Runner saves OUT for its normal result verification. Routing twice without
finalizing, finalizing twice, and inconsistent volume/depth/flow edits fail.

## Captured identity and recorded results

Runner binds settings to the actual captured INP SHA-256. The worker checks that
hash and the opened engine's flow units, then resolves node names through actual
native indexes and verifies native node types. Model enumeration order is never
used as an engine index. Editing the caller's Model after capture does not change
the run. Unsupported routing settings fail before native open.

`snapshot.backend_settings` retains the exact immutable binding. Backend identity,
numerical policy, OUT semantics, settings and final removal totals are persisted
in the execution record. Each backend declares its private artifacts before
execution, so Runner applies the same ownership, publication, digest verification
and failure-retention rules as it does for other output files.

The optional JSONL trace records its parameters, each node's previous/before/after
state, actual engine index, time interval, removed volume and pollutant quantities.
A normal end appends
a summary. `record_steps=False` disables the detailed artifact but keeps totals.
Partial files returned after failure have `complete=False`; an interrupted trace
must not be treated as a complete run. Callbacks, cancellation and timeouts retain
the main failure and separate cleanup diagnostics. Native process crashes retain
stderr and the worker return code in RunFailure.

## Water, quality and statistics

External withdrawal is applied after routing and quality transport. For each
node, native finalization adds the actual removed volume to the flooding and
node-outflow balances exactly once. It leaves ordinary SWMM rate integration
separate. It does not clip small external rates. A disconnected ponded node still
routes its inflow into storage even when the model has no links.

Withdrawal removes a completely mixed portion of node water: concentration stays
unchanged, while the quality balance loses `volume * concentration`. The worker
uses actual engine pollutant IDs and units, verifies cumulative native water and
pollutant removal against its ledger, and records `accounting="discrete-volume:1"`.
Pollutant quantities use mg, ug or count for MG/L, UG/L or #/L respectively. The
conversion uses SWMM's `28.317 L/ft3`, separately from its rounded hydraulic SI
volume factor. `IGNORE_QUALITY` produces `None` quantities rather than fabricated
zero loads. REPORT disabling suppresses tables without skipping continuity errors.

`backend_results.data["native_statistics"]` exposes node maximum depth, maximum
external/ordinary flooding flow, flooding volume, maximum ponded volume, flooded
seconds, peak dates, and `routing_step_mean_depth`. Depths are full node water
depths; the policy trace uses depth above the full-depth level. Native statistics
are updated after all nodes have been adjusted, once per active routing step.
They are not maxima of the sampled OUT series.

`statistics_metadata` records units and scope. `removed_volume` covers the entire
simulation. Other node statistics follow SWMM's active routing steps ending at
or after ReportStart, including the complete interval crossing that boundary.
The mean is an arithmetic mean of routing-step end depths, not a time-weighted
mean. Dates are SWMM serial days from 1899-12-30 in the model's calendar without
a timezone; the initial simulation date is retained if no strictly positive peak
occurred. Flooded duration includes retained ponded water even when withdrawal
is zero. REPORT AVERAGES affects OUT sampling, not these native statistics.

The OUT node-overflow slot is identified as `easysewer:system-flooding`: for
pondable nodes it contains external removal; for other nodes it contains ordinary
overflow leaving the system. Retained ponding is not external loss. The system
flooding series combines these rates. Integrating sampled OUT values is not an
alternative to the discrete ledger or native balances.

## Native source and validation scope

The branch packages rebuilt Windows/Linux custom libraries with ABI 201 and
adjacent `flexible_ponding.build.json` records. The pinned source, byte checks,
separate preparation and build instructions are in
[native/flexible_ponding](../native/flexible_ponding/README.md).
The control-rule-independent clock and bounded absolute paths are retained from
ABI 200. ABI 201 adds checked finalization, interval/quality/statistics accessors
and the accounting changes above. An older ABI is rejected explicitly.

The shared native I/O corrections check HOTSTART reads, writes and close
errors; handles read-only input and repeated close; and releases climate,
scratch and replaced TREATMENT resources. It shares the exact-source patch
implementation with the standard build while verifying each family's source
anchors. The custom source already had the corrected buildup count. Known
custom hashes advertise `easysewer:native-io-fixes:11`; ABI 201 alone does not
grant that capability to an unknown user library. Revision 11 adds
`easysewer:checkpoint:2` and the six shared initialization/scheduling corrections
listed in the [checkpoint recipe](../native/checkpoint/README.md). Withdrawal
policy 2 and accounting ABI 201 remain unchanged. Known revision 10 bytes retain
their previous I/O identity without a checkpoint claim. Revision 2 additionally
checks [RAIN headers, samples and runtime I/O](2.0-native-io.md), permits
read-only RAIN USE, and bounds historical rainfall text parsing.
Revision 3 adds [complete RUNOFF I/O checks](2.0-native-io.md), including staged
frame reads, checked SAVE and read-only USE, with no accounting ABI change.
Revision 4 adds [checked RDII binary/text reads and generation](2.0-native-io.md),
with separate capability `easysewer:rdii-io:1`. ABI 201 and withdrawal policy 2
remain unchanged.

Tests cover six flow units, independent direct-C execution, identity ordering,
HOTSTART initial storage, RULE_STEP and batch invariance, fraction endpoints,
callback failures, cancellation and failed native setters/return codes.
Additional physical cases cover all six hydraulic units and three pollutant
units, sealed nodes with and without links, shortened final steps, adaptive
hydraulic steps, delayed report starts, tiny removals, ordinary overflow,
disabled/averaged reports, ignored quality and binary-output-independent balances.
Overlong absolute input paths return a checked 303 error and release the worker.
Windows process launch has a separate current-directory length limit, so this
does not promise arbitrary working-directory lengths.

Direct C I/O regressions run separately against standard and custom libraries.
The custom tests cover malformed and read-only HOTSTART files, multi-pollutant
mass/byte layout, repeated failures/close, scratch descriptors and climate
ownership. Independent builds reproduce each platform's custom library bytes.

These cases qualify the stated withdrawal, accounting and resource contracts;
they do not certify every combination of SWMM processes. Typed [OUT](2.0-output.md)
and [RPT](2.0-report.md) readers have separate verification. Physical cache reuse,
remaining native input/output audits, the complete supported-platform matrix and
the other 2.0 release gates remain open. The shared RAIN recipe is independently
qualified and recorded in both the standard and custom build manifests.
