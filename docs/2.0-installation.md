# Installation

Python 3.10 or later is required. The 2.0 API does not support 1.x callers.

## Install version 2.1.0

```console
python -m pip install --upgrade easysewer==2.1.0
python -c "from easysewer import Model; print(Model())"
python -m easysewer doctor --json --smoke-test
```

Use a native 64-bit interpreter on a supported target and a current pip. Version
2.1.0 provides platform-specific Windows x64, Linux x64, Linux ARM64 and macOS
arm64 wheels containing both standard SWMM and the OUT reader, with non-system
runtime dependencies bundled. It also fixes Windows virtual-environment worker
launch without relaxing process identity checks. See the
[release notes](2.0-delivery.md#210-release-notes).

The immutable PyPI `2.0.1` release remains Windows/Linux x86-64 only, with Linux
requiring glibc 2.33+ and system `libgomp.so.1`. Its native `py3-none-any` wheel
tag does not establish compatibility on other platforms. Installing or retaining
2.0.1 does not provide ARM artifacts or the `doctor` command.

## Install a local build

Build the source archive and then the matching native wheel as described in
[testing and builds](2.0-testing.md). Install the final wheel from the build's
`wheelhouse/` directory, not the intermediate wheel in `raw/`. For example, in
a POSIX shell after a matching native build at `dist/native`:

```console
python -m pip install --force-reinstall dist/native/wheelhouse/*.whl
python -m easysewer doctor
python examples/v2_first_run.py runs/first-example
```

On Windows, pass the exact generated wheel filename to pip. Use a fresh virtual
environment when comparing a published release, local build and pure profile.
Native wheels contain only their selected platform's libraries and use truthful
platform tags; they are not `any` wheels. Python code does not depend on a
CPython extension ABI, but the bundled native libraries still require the correct
64-bit interpreter, operating system and native architecture.

## Native platform contract

The core native contract requires both standard SWMM 5.2.4 and the native OUT
reader. It covers these build targets:

| Target | Python process ABI | Minimum runtime | Final wheel platform tag |
| --- | --- | --- | --- |
| `windows-x86_64` | Windows x86-64, 64-bit | Compatible Windows x64 runtime | `win_amd64` |
| `linux-x86_64` | Linux x86-64, 64-bit | glibc 2.33 | `manylinux_2_33_x86_64` |
| `linux-aarch64` | Linux aarch64, 64-bit | glibc 2.28 | `manylinux_2_28_aarch64` |
| `darwin-arm64` | macOS arm64, 64-bit | macOS 14.0 | `macosx_14_0_arm64` |

Each target requires both the standard solver and native OUT reader. Linux
x86-64 preserves the existing compiled libraries and their glibc 2.33 floor;
it does not silently raise that floor to 2.34. Its `manylinux_2_33_x86_64` tag
states the verified PEP 600 glibc floor and is accepted by PyPI. Auditwheel's
2.34 policy is used only for dependency bundling, not as the final compatibility
claim. Final-byte checks enforce the 2.33 symbol floor, permitted system-library
closure, bundled SONAMEs and baseline CPU requirements; a separate clean 2.33
fixture must execute the wheel before release. Use a current pip and run doctor
in the actual deployment environment before simulation.

The wheel tag and `easysewer/libs/runtime-manifest.json` declare the runtime
contract. Final repair audits every bundled dependency against that contract
and hashes the final installed bytes. Linux aarch64 is built in its native
manylinux 2.28 environment. macOS builds on a native macOS 15 host set a 14.0
deployment target for the solver, OUT reader and pinned LLVM OpenMP runtime;
the build-host version is not the minimum supported runtime.

A declared baseline is not evidence that it was executed. The release gates
separately require clean glibc 2.33 x86-64 and AlmaLinux 8 aarch64 runtime checks.
The [dated macOS 14 observation](2.0-testing.md#observed-macos-14-baseline) records
one exact LLVM 23 wheel on macOS 14.8.9; 14.0 is the deployment target, not the
observed patch version. Continuing macOS CI uses 15 and 26 after removal of the
temporary 14 row. Do not assume a later rebuilt wheel inherits that recorded
baseline. Compatibility tests in an older Linux fixture are not a security-support
recommendation for that operating system. Inspect the matching final-wheel CI
evidence and run doctor in the actual deployment environment. No target pass is
asserted by this table.

Intel macOS, Windows ARM64 Python, ARM32, other 32-bit Python, musl Linux and
`universal2` are outside this contract. Rosetta, QEMU and other emulation do not
qualify a native ARM release. On Windows, the static ABI check uses the Python
build: x64 Python on an ARM64 host may reach the loader under Windows x64
emulation, but this is not native Windows ARM support or a qualified release
target. Native checkpoint archives bind exact engine bytes and ABI. Repairing
or rebundling a library can change that identity even on the same architecture;
checkpoints from an older wheel are not promised to resume with these wheels.
Retain the original runtime for those archives. This feature does not establish
cross-architecture checkpoint compatibility.

FlexiblePonding is an experimental, scientifically unvalidated example of a
replaceable backend. Existing x86-64 support is preserved; it is optional on ARM
and is not required for core readiness. Requesting FlexiblePonding when it is
unavailable produces an explicit error, never a silent standard-backend fallback.
See [the experimental backend guide](2.0-flexible-ponding.md).

## Diagnose native readiness

Both entry points run the same checks:

```console
python -m easysewer doctor
easysewer doctor
python -m easysewer doctor --json
python -m easysewer doctor --smoke-test --timeout 30
```

By default, doctor checks the runtime ABI, manifest, required native files,
hashes and dependency records, then loads each available library and checks its
ABI in a disposable process. It does not solve a model, create simulation files,
repair the installation, install dependencies or change system settings. Importing
the package does not perform these checks or load a solver.

`--smoke-test` explicitly adds a minimal standard solve and native output read in
a temporary directory. Cleanup is owned by the parent process, including after
a child crash or timeout. It does not run the user's model or write into the
current project. `--timeout SEC` limits each isolated check, not the whole command;
the default is 30 seconds and accepted values are finite, greater than zero and
at most 3600 seconds.

`--json` emits the versioned `easysewer:doctor:1` report with runtime identity,
per-library results, required/experimental flags, artifact/dependency evidence,
smoke-test status, `ready` and `exit_code`. Core readiness requires the standard
solver and OUT reader. Missing or broken optional FlexiblePonding is reported but
does not make an otherwise ready core fail.

| Exit code | Meaning | Next step |
| --- | --- | --- |
| `0` | Required native checks passed, including smoke test if requested | Proceed with model-specific validation |
| `2` | Invalid command-line usage | Check `python -m easysewer doctor --help` |
| `10` | Unsupported platform or Python ABI | Use a supported native interpreter/wheel, or the pure profile |
| `11` | Missing, corrupt or inconsistent required artifacts | Reinstall a complete matching wheel from a trusted build |
| `12` | Native loader, symbol or ABI check failed | Inspect the reported library/dependency and OS baseline |
| `13` | Worker launch/protocol failure, crash or timeout | Retain the report; check the environment and timeout |
| `14` | Requested smoke solve/output or temporary-file operation failed | Inspect the smoke diagnostic before using simulations |

Availability and a successful smoke run do not establish numerical validity,
hydraulic accuracy, scientific validation or all-platform floating-point
equivalence. They do not replace model validation and the relevant regression
and numerical qualification suites.

## Programmatic probing and troubleshooting

```python
from easysewer.runtime import StandardBackend

info = StandardBackend().probe()
print(info)
if not info.available:
    raise RuntimeError(info.reason)
```

`probe()` loads the selected solver in a disposable worker. Use
`FlexiblePondingBackend().probe()` only when the experimental backend is intended.
In contrast, `easysewer.get_native_capabilities()` is a lightweight file/platform
check: `True` means that a candidate file exists for this ABI, not that the loader
can load it or that its numerical behavior is validated.

Final repaired wheels bundle non-system runtime dependencies, including the
applicable OpenMP runtime. Users should not need a separate OpenMP or Homebrew
installation merely to run those wheels. A missing bundled dependency or hash
mismatch requires repairing/reinstalling the artifact, not pointing it at an
arbitrary system library. Do not copy libraries between architecture directories
or replace system libc files manually.

The old PyPI `2.0.1` wheel and checked-in legacy Linux x86-64 source artifacts
still depend on system `libgomp.so.1`. For those artifacts only, install the
system OpenMP package (`libgomp1` on Debian/Ubuntu or `libgomp` on Fedora/RHEL).
Reinstalling an unchanged wheel does not lower a glibc or macOS requirement.
An explicitly selected compatible user library is checked separately and is
not treated as a verified bundled build merely because it reports SWMM 5.2.4.
See [backend provenance](2.0-backend.md) and the
[standard build recipe](../native/standard/README.md).

## Pure modeling and result reading

The separate pure wheel contains neither native libraries nor execution workers.
It supports modeling, INP/JSON conversion and pure result reading without a
solver. It does not include a WebAssembly solver, and successful host-Python
execution does not establish browser support. Install one package profile per
environment. See [the pure Python build guide](2.0-pure-python.md).

The core runtime has no third-party Python dependencies. Quick Start plotting
requires Plotly, and interactive notebook execution also requires Notebook/Jupyter;
these are example dependencies. Package builds require setuptools 77.0.3 or later
and wheel; native compilation and repair have additional build-time tools listed
in [testing and builds](2.0-testing.md).
