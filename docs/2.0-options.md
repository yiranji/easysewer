# Candidate 2.0 analysis options and transformations

`normal_flow_limited` accepts `SLOPE`, `FROUDE`, `BOTH` and `NONE`. The string
`"NONE"` disables the native normal-flow limiter; Python `None` omits the option
and uses the profile default `BOTH`. This choice does not disable routing or
remove a conduit's separately configured maximum flow. See the
[record/variant acceptance matrix](2.0-support-matrix.md) for the distinction
between keyword coverage and complete contextual validation.

```python
from datetime import date, time, timedelta
from easysewer.model import Model

model = Model.from_inp("network.inp", strict=True)
model.update_options(
    start_date=date(2026, 9, 20), end_date=date(2026, 9, 20),
    end_time=time(12), rule_step=timedelta(seconds=20),
    routing_step=timedelta(seconds=0.5),
)
effective = model.effective_options
print(effective.defaults_used, effective.adjustments)
model.validate(for_run=True).raise_for_errors()
model.to_inp("network-edited.inp")
```

## Explicit and effective values

`Options` covers all 43 tagged SWMM 5.2.4 analysis-option keywords. Missing values
remain `None`; explicit zero, `False`, and the native default remain distinguishable.
`effective_options` applies the fixed profile defaults and static native adjustments
without modifying the explicit model. It returns resolved values, start/end/report
dates, native duration, defaulted fields, adjustments and diagnostics.

This is static resolution, not an executed engine snapshot. Object-dependent
ignore flags, actual thread count, file availability and backend capabilities are
part of later runtime preflight. Ordinary `validate()` accepts an incomplete run
period; `validate(for_run=True)` also checks the implemented run-period/step rules.

In particular, the solver can reduce `WET_STEP` to the recording interval of a
used time-series rain gage before adjusting `DRY_STEP`. Static option resolution
does not include that object-dependent adjustment. Actual runoff frames also end
at rain changes and the end of the simulation. Inspect executed results when the
actual schedule matters; configured and statically resolved values can differ
from the executed steps.

The fixed profile follows the tagged solver: for example, its unset `VARIABLE_STEP`
is 0.75 and unset end time is midnight. These differ from some manual descriptions.
Native duration uses double-precision day subtraction followed by flooring, so a
nominal two-minute period can resolve to 119 seconds. `duration` exposes that result
while `start` and `end` retain the calendar dates.

Calendar values use `date` and timezone-free `time`; `DayTime(day_offset=1)` represents
24:00 and `MonthDay` represents the non-leap sweeping calendar. All step options use
`timedelta`. The codec handles their different INP numeric units explicitly:

Calendar numeric components use ASCII decimal digits, with an optional plus sign.
Three-letter month names remain case-insensitive. Underscores and Unicode digit
forms are diagnosed and retained as invalid source: Python's integer parser would
otherwise accept dates that the native engine reads differently. The same rule
applies to sweeping dates and the shared date codec used by time series, controls,
events, climate files and rain-gage files.

The native engine initializes both omitted report-start components with its finite
`NO_DATE` sentinel (-693594 days), sums the components, then clamps to simulation
start. Usually a partial report calendar therefore resolves to simulation start.
Very large dates or clocks can exceed that fallback; run validation checks the
result against simulation end. A resolved calendar outside Python's date range
produces `options.calendar_overflow`. Explicit values and omission remain intact.

Native `hours:minutes:seconds` parsing uses signed 32-bit integer seconds. Colon
input above 2147483647 seconds is diagnosed and retained as invalid source. For
calendar clocks, control time constants and series times, the writer uses decimal
hours when necessary to avoid that overflow or preserve fractional seconds. Decimal
text is calculated from integral microseconds, so large public clocks survive INP
round trips without intermediate floating-point rounding. Native execution still
uses double-precision days; resolved partial calendars and OUT metadata can reflect
that precision. The calendar qualification checks actual saved output timestamps.

| Option input | Numeric interpretation | Clock input |
| --- | --- | --- |
| RULE_STEP, REPORT_STEP, WET_STEP, DRY_STEP | Decimal hours, native whole-second rounding | Whole seconds; fractional seconds are truncated with a diagnostic |
| ROUTING_STEP, LENGTHENING_STEP | Seconds, including fractions | Native whole-second interpretation |
| MINIMUM_STEP | Seconds, including fractions | Not accepted |

Programmatic RULE_STEP fractions are rejected rather than silently changed.
The writer uses clock notation for scheduled steps and numeric seconds for routing
and other fractional-second steps. Missing RULE_STEP and explicit zero both mean
native every-routing-step evaluation, but their source intent remains separate.

Negative scheduled durations are rejected and their original INP rows retained
with diagnostics. The native parser has a surprising decimal-time behavior:
`WET_STEP -1` and `DRY_STEP -1` become 23 hours. The public duration contract does
not adopt that wraparound. Zero wet/dry steps are rejected by both the model and
the solver. Positive decimal hours round to native whole seconds; fractional
colon seconds truncate, with a coercion diagnostic.

Categorical values and booleans use the complete spellings listed by the fixed
profile (plus the documented routing aliases). The native matcher accepts
arbitrary suffixes such as `YES_FUTURE`; the typed reader diagnoses these
values and retains their original rows. Missing values, extra columns,
non-finite numbers and Python-only numeric syntax are also diagnosed.
Well-formed numeric THREADS/MAX_TRIALS tokens retain native integer-prefix
coercion: `2e3` means 2, with a diagnostic; arbitrary trailing junk is invalid.

Repeated known options follow native source order. Untouched source remains byte
exact. Editing any option regenerates the owned option assignments as one ordered
block, retaining comments and unknown records. Legacy `FLOW_ROUTING NONE` is read
as a routing-disable assignment and normalized into `flow_routing` plus
`ignore_routing`; the domain routing value is STEADY, KINWAVE or DYNWAVE. Unknown
or invalid rows are retained and diagnosed, not claimed as supported.

## Intentional context changes

```python
model.convert_units("CMS")                    # fixed engine profile factors
model.convert_units("CFS", basis="physical")  # exact physical unit definitions
model.convert_link_offsets("ELEVATION")       # each endpoint's invert elevation
model.reinterpret_units("CMS")                # keep numeric values unchanged
```

Once model data exists, direct changes to FLOW_UNITS, LINK_OFFSETS or
FORCE_MAIN_EQUATION require a conversion or reinterpretation operation, including
setting/removing an explicit default. `reinterpret_link_offsets()` validates the
result transactionally. `reinterpret_force_main_equation()` explicitly changes
roughness interpretation; it does not claim to convert between friction equations.

Engine conversion defaults to the profile's tagged constants. SWMM's rounded
flow, volume, land-area and wind factors differ slightly from physical definitions.
Standalone `UnitContext.convert()` uses physical definitions unless `rules=` is
explicitly supplied. Conversion treats map coordinates, codes, counts and slopes
according to their dimensions, and Darcy-Weisbach force-main roughness as a length.
Selecting engine factors is not a universal promise of identical hydrographs:
storage area/volume factors are inconsistent in the fixed engine, and kinematic
iteration can amplify one-ULP changes. See the measured limits in
[storage and divider nodes](2.0-nodes.md).

Model conversion constructs all replacements before committing and rolls back on
validation failures. Unknown source, missing dimensions and unsupported formula
coefficients prevent partial conversion. Offset conversion covers both conduit
endpoints and the inlet offsets of orifices, weirs and outlets; pumps are unchanged.
See [regulators](2.0-regulators.md) for coefficient units and native clamps.
The `*` node-invert marker is allowed only with ELEVATION offsets.

Known file references carry their origin and input/output direction. `to_inp()`
rebases them in an export copy; `path_policy` accepts relative, absolute or preserve.
The in-memory model is unchanged. Unparsed source that may contain external paths
prevents moving the INP to another directory until that feature is structured.

## Validation and limits

Tests exercise all 43 options, repeated assignments, legacy routing aliases,
explicit defaults, native precision, path rebasing and transactional failures.
Native 5.2.4 tests compare complete control-action timing, depth/flow histories and
mass balance for missing/zero/decimal/clock/over-24-hour RULE_STEP, fractional-second
routing and DEPTH/ELEVATION conversion. The six flow-unit variants also match the
same native internal hydrograph within strict numerical tolerance.
