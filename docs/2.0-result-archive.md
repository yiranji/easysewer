# Complete result archives

`RunResult.save(directory)` captures a returned run and every registered file in
a new self-contained directory. `RunResult.load(directory)` verifies and restores
the typed result without probing a backend, loading a native library or rerunning
the model. This works for `succeeded`, `rejected`, `failed`, `cancelled` and
`timed_out` results.

```python
from easysewer.runtime import RunResult

result.save("archives/storm-001")  # parent directory must exist
# The whole storm-001 directory can now be copied or moved.
restored = RunResult.load("archives/storm-001")
restored.raise_for_status()
with restored.open_output() as output:
    flow = output.series(None, "swmm:inflow")
print(restored.report_table("swmm:node_depth"))  # if requested during the run
```

The archive includes the original model/config JSON bytes, executed INP,
snapshot/profile/effective options, resource records, backend identity and
settings, native object order, continuity and applicability, requested tables,
OUT metadata, report decoding and messages, produced/consumed cache evidence,
custom backend results and all `FileArtifact` contents. Complete OUT files retain
all saved series; loading does not materialize those series into memory. LID
detail files and custom ponding traces remain registered artifacts. Captured
report tables retain their original typed cells and provenance, including tables
with extension keys; loading them does not require their parsing plugin.

A failed run retains exactly the evidence returned by Runner: primary and
cleanup errors, stderr, return code, any retained incomplete artifacts, and the
best-effort report capture with its truncation flag. If Runner intentionally
removed working files, saving cannot recover those deleted files. It still saves
the in-memory snapshot, diagnostics and report capture that actually exist.

## Paths and provenance

The 1.1 format adds `RunResult.continuations`, an immutable sequence of
`RunContinuation` records. Each record identifies a resume attempt, the original
execution, both Runner and solver checkpoint digests, its restored clock/step
boundary, a timezone-aware attempt start, and the attempt's runtime config.
The original snapshot identity is preserved. Simulation settings cannot change
through this record; output destinations and operational limits can differ.
History is retained for unsuccessful results even when no files were kept.

Version 1.0 archives remain readable and explicitly migrate to an empty history.
Version 1.2 additionally retains structured diagnostic subjects,
related objects and labelled original locations. Versions 1.0 and 1.1 migrate
missing diagnostic metadata to empty values. Legacy writers reject nonempty new
metadata instead of silently discarding it; the 1.0 writer also rejects nonempty
continuation history. Runner scheduling/resume is integrated; ordinary fresh
runs have an empty history. These records are provenance, not signed proof of
a native restoration.

File-only saving writes 1.3. Directory-bearing results select the minimum
applicable version from 1.4 through 1.9, as described below. Reports are stored once as original bytes with their requested
encoding, source and decoder profile. A fingerprint covers every decoded field,
including text, blocks, repaired offsets and diagnostic contexts. Loading
reconstructs and verifies this evidence; a changed decoder cannot silently
replace it. Large detail reports therefore do not duplicate their full text and
each block's text inside the JSON manifest. Versions 1.0–1.2 remain readable;
older readers explicitly reject unsupported later versions. Result-table JSON
remains 1.2. Runner checkpoint context envelopes retain their codec version;
the inner checkpoint selects a directory-capable version when necessary.

On load, `FileArtifact.path` points inside the archive. Its role, owner, field,
digest, size, completion and declared destination are preserved. All artifact
bytes are verified at load; later `read_bytes()` and `open_output()` still detect
modification. `report_reader()` queries immutable captured report bytes, while
`read_lid_report()` verifies the archived detail artifact.

Original paths in snapshots, resource records, diagnostic spans, requested
table sources, backend metadata and `retained_directory` are historical
provenance. Loading never reads or writes those paths. Newly queried OUT series
and newly parsed report tables identify their actual archived file location.
The manifest also retains each artifact's original path from the object saved.

`snapshot.model()` still reconstructs the original model, with its original
file references, and requires an explicit schema for extension models. Loading
an archive does not rewrite the captured INP, translate foreign-platform model
paths, install an engine or prepare that model for a new simulation. Cache
evidence from `restored.produced_caches` can be passed explicitly to a subsequent
Runner; that Runner performs the usual engine/layout/condition checks. Its
HOTSTART applicability remains partial.

## Integrity and failure behavior

Version-specific JSON Schemas are available for the `result.json` structure:
[1.0](result-archive-1.0.schema.json), [1.1](result-archive-1.1.schema.json),
[1.2](result-archive-1.2.schema.json), [1.3](result-archive-1.3.schema.json),
[1.4](result-archive-1.4.schema.json), [1.5](result-archive-1.5.schema.json),
[1.6](result-archive-1.6.schema.json), [1.7](result-archive-1.7.schema.json),
[1.8](result-archive-1.8.schema.json), and [1.9](result-archive-1.9.schema.json).
Select the schema matching the envelope's `schema_version`. See the
[schema contract and validation evidence](2.0-result-schemas.md) for its scope.

The versioned `result.json` envelope (`easysewer:run-result`, schema `1.3` for file-only results, or `1.4`–`1.9` for directory evidence)
describes a closed set of data types and a SHA-256 inventory. Binary payloads and
files live in `blobs/<digest>`; identical bytes share storage. There are no
pickles, dynamic imports or serialized native pointers. Unknown versions/types,
duplicate JSON keys, malformed typed fields, missing or extra blobs, changed
bytes, inconsistent snapshot/cache ownership and contradictory completion flags
are rejected. Stored OUT layout is checked against the actual OUT bytes, and
captured report decoding is checked against its raw bytes.

Saving refuses an existing destination, including an empty directory or symlink.
It verifies source artifacts while copying, writes the manifest last and removes
only its newly owned directory on an ordinary exception. A process or machine
crash can leave an incomplete new directory; loading rejects incomplete content.
This is not a crash-recovery journal or a multi-file update operation.

`max_bytes` defaults to 8 GiB of unique payloads. `max_manifest_bytes` defaults
to 64 MiB and bounds the manifest and, separately, the combined in-memory
evidence payloads (such as report/model/table bytes). Both limits can be raised
explicitly at save and load. File copying and hashing are streamed; a large OUT
does not have to fit in that memory budget. Ordinary result construction does
not access the filesystem. These are source-payload limits, not a bound on total
Python memory: decoding reports still creates strings, blocks and diagnostics.

The archive budget is independent of `RunConfig.report_read.max_bytes`.
Increasing the latter allows a larger report to be captured during a run; it
does not increase the budget for restoring that report from an archive. For
example, a full-year report of approximately 455 MB needs an explicit archive
evidence budget at both save and load:

```python
evidence_budget = 512 * 1024**2
result.save("annual-result", max_manifest_bytes=evidence_budget)
restored = RunResult.load("annual-result", max_manifest_bytes=evidence_budget)
```

Choose this budget for the combined report, model and table source payloads.
The example does not promise a 512 MiB process-memory ceiling. Keeping the
default budget deliberately rejects such a large report even when its run
completed successfully.

Checksums establish consistency with the archive's declared content. They do
not authenticate the producer or establish hydraulic accuracy. A restored
backend record describes the original execution, not an engine available on the
current host. This result archive is separate from a full simulator checkpoint;
it cannot continue an interrupted solver.

## Directory evidence and versions

The archive includes `directory_artifacts` and `directory_group_artifacts`, with
file contents, empty directories, initial and current state, absence when
declared, and internal hardlink relationships. Shared and nested consumers retain
their own identities while a common captured tree records their relationship.
Archive blobs remain content-addressed; equal file bytes alone do not declare a
hardlink. Loading reconstructs only archive-owned trees, without visiting the
original source paths, and rejects changed or extra content.

| Result version | Additional representation |
| --- | --- |
| 1.4 | Directory manifests and artifacts |
| 1.5 | Separate initial evidence for writable private inputs |
| 1.6 | Explicit absent optional directory state |
| 1.7 | Internal hardlink topology |
| 1.8 | Shared/overlapping directory groups |
| 1.9 | File and directory consumers in the same group |

Readers accept 1.0–1.9 with explicit defaults for missing older fields. A writer
asked to use an older codec rejects values that need newer fields. It never
downgrades by discarding directory evidence. Result archives are distinct from
checkpoint containers: their version numbers describe different envelopes.
See [directory resources](2.0-directory-resources.md) for ownership and limits.
