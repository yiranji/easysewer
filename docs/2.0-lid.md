# LID controls and deployments

The candidate `easysewer.model.Model` exposes `lid_controls` and `lid_usage`.
Definitions are shared named `LidControl` records. Deployments reference a
definition and a subcatchment without copying either object. Both collections
participate in graph rename/delete, validated transactions, JSON, scenarios,
unit conversion and independent source-free INP reconstruction.

```python
from easysewer.model import Ref
from easysewer.model.lid import LidControl, LidStorage, LidDrain, LidUsage

# model already contains subcatchment Roof.
model.lid_controls.add(LidControl(
    id="Barrel", kind="RB",
    storage=LidStorage(thickness=36, void_ratio=1, seepage_rate=0,
                       clogging_factor=0, covered=True),
    drain=LidDrain(coefficient=10, exponent=.5, offset=0, delay=6),
))
model.lid_usage.add(LidUsage(
    record_id="roof-barrels", subcatchment=Ref(collection="swmm:subcatchments", key="Roof"),
    control=Ref(collection="swmm:lid_controls", key="Barrel"), number=34,
    area=12, width=0, initial_saturation=0, from_impervious=17, to_pervious=True,
))
```

These example numbers use US project units. A deployment's `area` is the area
of **each** replicate in ft²/m²; subcatchment area uses acres/hectares. Capture
percentages apply to the non-LID impervious/pervious area and are counted once
per deployment, without multiplying them by the replicate count.

## Definitions and layers

`kind` supports BC, RG, GR, IT, PP, RB, RD and VS. The following immutable layer
values retain all documented input parameters:

| Field/type | Parameters |
| --- | --- |
| `surface: LidSurface` | storage depth, vegetation fraction, roughness, percent slope, side slope |
| `soil: LidSoil` | thickness, porosity, field capacity, wilting point, conductivity, conductivity slope, suction |
| `pavement: LidPavement` | thickness, void ratio, impervious fraction, permeability, clogging factor, optional regeneration days/fraction |
| `storage: LidStorage` | thickness, void ratio, seepage, clogging factor, optional covered flag |
| `drain: LidDrain` | coefficient, exponent, offset, dry-weather delay, optional opening/closing heads and curve Ref |
| `drain_mat: LidDrainMat` | thickness, void fraction, roughness |
| `removals: tuple[LidRemoval, ...]` | pollutant Ref and removal percent |

Pavement/storage void ratios mean void volume divided by solid volume. Drain
mat void fraction means void volume divided by **total** volume. Soil porosity,
vegetation fraction and drain mat fraction are separate fields with separate
meanings. In particular, there is no generic unqualified `porosity` parameter
shared across every layer.

The manual recommends surface/soil/storage for BC, surface/soil for RG,
surface/soil/drain mat for GR, surface/storage for IT, surface/pavement/storage
with optional soil for PP, storage/drain for RB, surface/drain for RD and surface
for VS. Native 5.2.4 accepts some implicit zero layers beyond this table. Model
validation distinguishes required native layers from warnings for omitted
recommended layers, and supports PP with and without soil/storage and BC
without storage. Additional recognized layers are retained, including an RG
with storage/drain. Unknown layer subtypes require an explicit feature adapter.

Validation checks soil ordering/conductivity, pavement permeability/voids,
storage void ratio, drainage thresholds, swale depth/slope/roughness/width,
local fractions and percentages, total replicated area and capture totals.
Aggregate area/capture checks use the native 0.1% tolerance and rounded native
area conversion constants. Ordinary collection updates can hold an invalid
draft; validated transactions, export and run validation reject it.

Two manual/source discrepancies are explicit:

- An omitted rain barrel `covered` value means **NO** in the reviewed 5.2.4
  source and bundled solver, while the manual says YES. `None` retains the
  omission and produces a warning. Specify `True` or `False` deliberately.
- Native validates storage void ratio before forcing a barrel's void fraction
  to one and seepage to zero. A positive-height barrel with zero void ratio
  fails with the bundled solver, including the manual's sample configuration.

## Deployment identity, input order and defaults

Every active `LidUsage` has a positive integer `number`, per-replicate area and
width, initial saturation, impervious capture, return-to-pervious flag, and
optional report file, drain target and pervious capture. Initial saturation
sets soil moisture between wilting point and porosity and fills storage/drain
mat depth; it does not initialize ponded surface/pavement depth.

SWMM has no deployment ID. `record_id` belongs to Model/JSON/scenario and is
never emitted as an invented INP column. Imported rows receive `lid-usage-1`,
`lid-usage-2`, etc. JSON preserves these identities through rename/reorder;
reimporting INP assigns identities from its new row order. Multiple rows with
the same subcatchment and control remain independent. Native evaluates its
linked deployment list in reverse input order; the codec preserves input order
instead of sorting or merging it.

Zero-replicate input is a distinct `DisabledLidUsage`. Native checks its
subcatchment/control and minimum token count, then ignores the rest. The value
retains those remaining tokens in `parameters`, including invalid numeric
text, inactive paths and nonexistent drain names. They are inert data, with no
file consumers, references or guessed physical units. Converting project units
does not reinterpret them. Activation requires replacing the value with an
explicit, valid `LidUsage`; it never silently activates unconverted tokens.

Native integer-prefix parsing (for example `2.7` becomes 2) and positive
ToPerv flags are recognized with diagnostics. Optional interior `*`/zero
placeholders are emitted when needed. A literal `*` cannot be an explicit
report filename or drain target because native treats it as absent.

Type/layer assignments and pollutant removal assignments use their final
effective values. Every recognized source line is checked before claiming its
control. DRAINMAT is read only after a GR type declaration; an earlier ignored
line remains byte-preserved with a diagnostic. An unchanged source retains
comments and spelling. Editing the LID feature reconstructs its layered blocks
in type-before-layer order and its deployments in collection order. Original
comments remain; normalized output removes obsolete assignments. Run preflight
also checks resource names in obsolete source assignments, which native still
parses before applying the final value.

## References, units and external files

`drain_to` explicitly references either `swmm:nodes` or `swmm:subcatchments`.
Native resolves a matching subcatchment before a node. A requested node whose
name is shadowed by a subcatchment is rejected rather than silently redirected.
An omitted target inherits the parent subcatchment outlet. ToPerv returns
surface runoff to available pervious area; it also returns drain flow when
the effective drain outlet is the same as the subcatchment outlet. A fully
impervious or fully LID-covered catchment cannot accept that return flow.

Dimensions use rain depth for layer thicknesses/heads and rain intensity for
conductivity/permeability/seepage. For ordinary drains, converting the
coefficient multiplies it by intensity factor / depth factor ** exponent.
For RD the coefficient is gutter capacity, so only the intensity factor applies.
Drain control curves declare `(rain_depth, ratio)` dimensions and CONTROL kind;
shared-resource validation rejects incompatible other consumers. Per-pollutant
removal percentages register with the public pollutant-unit protocol and stay
unchanged during MG/L ↔ UG/L conversion.

`report_file` is an output `FileReference`. Its `FileUse` declares native process
working-directory resolution and write access. `resolve_files` can make the
path explicit, while `check_files` checks parent paths, existing outputs and
collisions without creating anything. Native opens these files during input
reading, including when rainfall is ignored. The common file policy therefore
keeps active deployments' outputs active in that case. Detailed report bytes
are compared against the independently written literal model in native tests.
Structured result-table reading and Runner ownership remain result/runtime gates.

## State and cache limits

No LID fields are invented in HOTSTART or RUNOFF binary layouts. Native
HOTSTART omits layer moisture, clogging history, regeneration and drain state;
`lid.hotstart_state` warns that deployments restart from their initial values.

RUNOFF stores total reported subcatchment runoff, including LID drainage,
without separate drain destination or removal fractions. Replaying it skips
LID calculations. `lid.runoff_state` warns that detailed performance/state is
not recomputed. A drainage-capable deployment with a distinct drain outlet or
pollutant removal produces the run error `lid.runoff_drain_semantics`, because
the aggregate cache cannot encode those separate semantics. A real native
save/use case with an alternate outlet proves changed node inflow and water
quality. Binary read/rewrite/consume equality alone does not prove physical
reuse is appropriate; authenticated producer snapshots remain a Runner gate.

## Validation and limits

Pure tests cover all variants, source-free JSON, scenarios, reference edits,
rollback, unit/resource contracts, bad inputs, multiple deployments, disabled
tokens and report-file preflight. Native tests compare full hydraulic/system/
report and two-pollutant histories against independent literal inputs: all eight
types, US/SI, optional layers, six flow units, shared definitions, reordered
deployments, alternate drain targets, initial saturation, return flow,
thresholds/curves, clogging/regeneration, dry delay, cover flags and removals.
