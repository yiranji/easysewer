# Cache production conditions

Cache layout checks establish names, order, units and bytes. They do not show
whether cached hydrology represents a changed model. The candidate runtime now
records a separate, versioned comparison of captured production conditions.
This comparison does not promise fresh-solve equivalence, conservation or a
complete hydrologic continuation state.

`ProducedCache.reuse_evidence` binds a `CacheContext` to the cache SHA-256.
Runner publishes this as `run:cache-evidence`, alongside the unchanged cache
manifest. It compares the consumer's captured input and resources before
opening the solver. `RunResult.consumed_caches[i].reuse` gives:

- `matched`: every condition in the registered policy matches, with no missing
  evidence under that policy;
- `changed`: identified conditions differ; `differences` names the domains;
- `unknown`: evidence, a supported profile or a comparison adapter is missing.

The comparison preserves whether evidence came from a supplied Runner product
or a caller assertion. Evidence is inspectable data, not a signed attestation.
Loading a sidecar does not make its claims trusted or execute a plugin.

## Choosing a reuse purpose

```python
from easysewer.runtime import RunConfig, Runner
from easysewer.model import FileReference

settings = RunConfig(
    output_directory=FileReference(path="consumer-run", direction="output"),
    cache_reuse=(("RUNOFF", "require_match"),),
)
result = Runner().run(consumer_model, settings, producers={"RUNOFF": produced})
```

The three intents are:

| Intent | Behavior |
| --- | --- |
| `inspect` (default) | Compare conditions, retain differences and warn about limited/changed scope |
| `require_match` | Reject changed/unknown conditions before native open; preserve existing outputs |
| `frozen` | Explicitly reuse historical values while retaining and warning about the comparison scope |

`frozen` can be appropriate for downstream hydraulic scenarios with deliberately
fixed runoff. It does not claim the groundwater history would be reproduced by
the modified receiving network. Existing byte, layout, engine, inspection and
resource-integrity checks still apply to all three intents.

`require_match` checks recorded production conditions. RUNOFF remains sampled
data: matching conditions do not restore infiltration memory, snow/LID states,
buildup or groundwater evaporation omitted from the format. Continue checking
[result applicability](2.0-result-applicability.md).

## Current RUNOFF policy

`swmm:runoff-production-conditions:1` captures supported SWMM 5.2.4 input and
qualified backend behavior. It compares the complete supported hydraulic and
hydrologic collections, effective analysis options, simulation calendar,
external input contents, initial interface files and physical backend settings.
This includes groundwater receiver/bottom/area, rainfall and climate, snow,
infiltration, water quality, LID layers/deployments and network feedback.

Hydraulic state matters: groundwater exchange can depend on receiver depth,
inflow and available node volume. Equal aquifer parameters alone are insufficient.
The policy conservatively includes all supported physical collections, including
unused definitions; a reported difference is not proof of a numerical change.

Title, map/positions, report selections/averaging/disabled flags, report start,
temporary directory, output destinations and trace destinations are excluded.
External paths are compared by captured content hashes, so relocating identical
data is allowed. The report interval remains a production/sampling condition,
as it can constrain effective execution steps. Unknown input, profiles, backend
settings or uncaptured resources remain limited; no missing file is opened merely
to infer compatibility. RUNOFF binding paths and SAVE/USE mode are excluded from
the hydrology comparison itself.

## RDII history and HOTSTART continuation

Two additional adapters use the same evidence/intent contract, with different
time relations. They conservatively compare all supported physical collections,
options, captured input contents and backend settings described above. This can
reject an edit to an unused or irrelevant definition; `changed` does not itself
prove a numerical difference. An adapter does not open missing resources to
manufacture evidence for a match.

| Policy | Time requirement for `matched` | Meaning and limits |
| --- | --- | --- |
| `swmm:rdii-production-conditions:1` | Same simulation start; consumer end within producer end | Compare the antecedent rainfall/initial abstraction history and declared coverage of the binary RDII process |
| `swmm:hotstart-continuation-conditions:1` | Consumer start equals producer end | Compare declared conditions for loading a partial HOTSTART4 state at the next hydraulic boundary |

RDII includes seasonal RTK components, initial abstraction, recovery, rain gages,
monthly rainfall adjustments, sewer areas and node bindings. Its records use
absolute dates and internal CFS, with native node indices. Native production
omits zero-flow intervals, and a completed dry run can produce a header-only
file. Consequently coverage comes from the completed producer calendar, not
the first/last nonzero frame. Extending that calendar is a difference, including
for a dry cache. Starting later also differs: a fresh run would reset the unit
hydrograph convolution and initial-abstraction memory. To deliberately retain
the longer antecedent history, use `frozen` and inspect the recorded difference.
Text RDII remains supported by its existing named-node interface checks; this
binary production policy cannot certify a text file merely because its hash is
attached to an asserted sidecar.

HOTSTART4 stores hydraulic depth/flow/setting/quality, storage residence time,
subarea depths/runoff, infiltration memory, selected groundwater/snow states,
and subcatchment quality/buildup/sweeping state. It does not store a complete
solver checkpoint: LID states, RDII convolution/abstraction memory, control,
climate/gage and solver integration history are omitted. The saved runoff state
may belong to a runoff step past the hydraulic end. Hydraulic floats also lose
precision when saved. Loading the file initializes a new numerical integration.

For this reason a known produced HOTSTART is `partial` in
`ProducedCache.applicability` even when continuation conditions are `matched`.
Native tests compare an uninterrupted LID run with two adjoining runs and
demonstrate different runoff values despite matching declared conditions.
Neither `require_match` nor a complete layout manifest promises complete or
bitwise identical continuation. The policy records the partial state scope in
its evidence; changing that scope to claim a complete checkpoint is unsupported.

Elapsed inline time series restart at the new simulation origin, so a shift in
that origin is a condition difference. External time series, controls and climate
files are conservatively bound to their originating simulation start as well;
this adapter does not attempt to prove that their contents are independent of
that origin. Calendar-dated inline series can span a boundary without that
particular difference. Initial model fields remain compared even if a stored
state would override some of them. Changed geometry, aquifer parameters or
state interpretation are also retained as differences. The HOTSTART policy is
for version 4; legacy versions retain format/layout support and unknown condition
scope, rather than inheriting a version-4 assertion.

Kinds without a registered adapter keep `unknown` condition scope; requiring a
match rejects them explicitly. Existing byte, layout, engine and post-capture
integrity guards apply to all three adapters.

## Persistence and extension

```python
from easysewer.runtime import CacheEvidence

portable = CacheEvidence.from_bytes(produced.reuse_evidence.to_bytes())
result = Runner().run(
    consumer_model, settings,
    interface_manifests={"RUNOFF": produced.manifest},
    cache_evidence={"RUNOFF": portable},
)
```

Portable evidence uses `easysewer:cache-evidence:1`; unknown policy data can
round-trip but cannot yield a match without an explicitly registered adapter.
Old manifests and products without condition evidence remain limited. Condition
evidence does not substitute for a positional layout manifest.

Trusted applications can register immutable `CachePolicy` entries in
`CachePolicies` and pass the registry to `Runner(cache_policies=...)`. Each
adapter has a versioned key, one cache kind, a snapshot capture callback and a
comparison callback. Unknown policies never trigger code loading. Duplicate
policy/kind registrations are rejected. The built-in policy preserves existing
contracts; future cache domains can be added through explicit adapters.

Execution records retain consumer contexts and comparisons; producer context
sidecars retain the captured facts. Full archived `RunResult` restoration,
complete hydrologic checkpoints and broader native/performance validation remain
separate release gates. The RDII native malformed-input/EOF audit is also a
separate gate; adding a condition adapter does not repair its C reader.

Cache preparation under Runner participates in the run's cooperative work scope,
including built-in INP context reconstruction and plain JSON fact comparison.
`FileArtifact.read_bytes(checkpoint=...)` optionally verifies an artifact in
bounded read/hash batches and returns the same complete bytes after size and
SHA-256 checks. With no active scope it retains the ordinary whole-read path.
Callback exceptions keep their identity and are not converted into an ordinary
cache mismatch. The artifact can be read again after interruption; callers must
still avoid concurrent file changes. The complete-bytes API retains the full
result in memory; the cooperative implementation also holds chunks while joining.
It is not a streaming-result API or a memory-budget guarantee.

Compare an interrupted cache consumer's retry with the same uninterrupted
consumer configuration. Fresh production and cache replay can already differ;
producer-versus-consumer byte equality is not an assumed invariant.

During Runner result finalization, built-in HOTSTART, RUNOFF and RDII layout and
payload validation participate in the inherited cooperative scope, including
large single frames. Captured-byte hashing and private result reads use bounded
batches. Manifest construction and pretty JSON encoding retain the existing
complete bytes and schema. Callback failures are not treated as invalid cache
facts and retain their original exception identity; interrupted immutable input
can be retried. These inherited checks do not add public callback parameters to
every cache method or alter existing producer/replay equivalence boundaries.

The complete-byte and complete-JSON APIs still allocate their full results;
chunked reads and encoding can additionally hold intermediate chunks during
joining. A single scalar, C/OS call, allocation, sort, join or arbitrary extension
operation remains interruptible only at its boundaries. Independent direct
operation timers and concurrent overhead observations do not replace full
process-tree memory and end-to-end cancellation/performance acceptance.
