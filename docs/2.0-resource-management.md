# Files, directories and runtime resources

Runner captures input resources, records their identities, digests and ownership, computes in a working directory, then checks results before publication. Always inspect the returned status. See [FILES and preflight](2.0-files.md) for file resources and [directory resources](2.0-directory-resources.md) for directories.

## Ownership and failure

- Inputs, generated files, directory members and existing outputs are recorded separately. A failure must not publish partial artifacts as complete results.
- File and directory scanning, resource budgets, cancellation and timeouts follow the run policy. Callback checks are cooperative; a callback cannot forcibly interrupt a single system call.
- Native sessions own libraries and streams in separate processes. Cleanup errors remain in diagnostics without replacing an earlier error.
- Long paths must satisfy the platform, backend and specific file-format constraints. Over-limit paths are explicitly rejected. After releasing resources, correct the input and retry.
- Intermittent Windows publication sharing conflicts remain in [known issues](2.0-known-issues.md). Journal ownership, state and retry rules are documented in [run recovery](2.0-run-recovery.md).

## INP preflight

Runner checks each physical line using its actual emitted UTF-8 bytes. Content is limited to 1023 bytes, including data, comments, whitespace and section headers. LF, CRLF and final-line terminators do not count toward content length. An internal standalone CR is rejected; a single trailing CR is accepted.

NUL and Ctrl+Z are rejected even in comments. Errors include source file, line and character column. Sources in other encodings are checked against their runtime UTF-8 size; Runner does not write a UTF-8 BOM. Drafts retain original bytes, while run preflight checks the actual rendered input.

Climate, rainfall, time-series and binary cache formats have their own limits rather than inheriting the INP line rule. See [native I/O contracts](2.0-native-io.md).

## Checkpoints and archives

Checkpoints bind exact library bytes, model, configuration and immutable inputs. Changing a library requires a new execution. Result archives store execution evidence and HOTSTART stores part of the solver state; neither is a complete execution checkpoint. See [checkpoint scope](checkpoint-support.md) and [result archives](2.0-result-archive.md).

## Native path and scratch-stream ownership

Input time-series and rain-gage filenames are allocated to their actual length in the project memory pool. Ordinary lookup and climate cursors borrow the same names; releasing a cursor does not free a borrowed name. Climate streams must close before project objects and the name pool are freed so close-error reporting can still safely reference filenames. Checkpoints record identities and resource keys, not addresses.

A successfully created scratch stream is handed directly to its OUT, RAIN or RDII owner. On POSIX, `fdopen` takes ownership of the descriptor. On Windows, the HANDLE is handed to a CRT descriptor and then to FILE. A failure at each layer closes only resources that layer owns and removes the file created by that operation. Explicit TEMPDIR is relative to the INP directory; creation or ownership-transfer failure does not silently fall back to another directory.
