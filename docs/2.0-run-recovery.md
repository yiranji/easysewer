# Recovering an interrupted local run

Runner creates a private `.easysewer-recovery-<token>.json` journal beside its
first reserved output and an adjacent `.lease` file. Each output reservation
records the journal path. An ordinary successful run or clean failure removes
these files. A process exit or cleanup conflict retains them. The journal is a
trusted local transaction record, not a portable RunResult archive.

To find journals and incomplete initial writes in a known output directory:

```python
from easysewer.runtime import discover_run_recovery

for item in discover_run_recovery("/absolute/output/directory"):
    print(item.state, item.journal, item.files, item.issues)
    if item.recovery is not None:
        print(item.recovery.run_id, item.recovery.phase)
```

This candidate API scans only the directory's immediate entries and groups
exact recovery journal, lease, pending-write and archive-copy names. It does not follow
matching symlinks or read pending JSON, and it changes no artifact bytes or names.
Unrelated names and nested directories are outside the scan. A missing or
inaccessible directory raises an error. A bad group is reported independently
so it does not hide other groups.

`RunRecoveryFiles.state` has these meanings:

- `recoverable`: the canonical journal was validated under its matching lease.
  `recovery` contains a `RunRecovery` observation. A subsequent recovery attempt
  still rechecks ownership and can fail or return a conflict.
- `incomplete`: no canonical journal was observed. This includes an initial
  lease with no journal, complete or partial pending writes, and pending-only
  remnants. Pending writes are never promoted to recovery authority. An initial
  writer can be between file creation and lock acquisition, so this state does
  not establish that the writer has exited or grant deletion permission.
- `busy-or-inaccessible`: the lease could not be acquired because it is held or
  permission was denied. This does not claim a specific process is alive.
- `unavailable`: a canonical journal lacks its lease, a file is invalid or was
  replaced, its read budget is exceeded, or another inspection error occurred.
  `issues` records the reason. Matching directories and symlinks are also reported
  here without opening them as recovery files.
- `retiring` or `retired`: an explicit retain decision has been recorded, with
  reservation release still pending or finished, respectively. Its `recovery`
  observation includes the recorded reason and reservation diagnostics.
- `archiving`, `archived` or `archive-conflicted`: an initial-artifact archive
  guard has been verified. `archive` contains its `RecoveryArchive` observation;
  `recovery` remains `None` because no run journal was adopted.

`journal` is the expected canonical path and need not exist; `files` lists names
observed during the scan, not a durable inventory. Discovery is advisory and
cannot authorize cleanup, release a reservation, or prove a whole directory is
free of running jobs. `max_bytes` applies separately to each canonical journal
with the same default and validation as inspection below. The initial remnants
and conflicts requiring explicit retirement still need a safe management end
state; directory discovery alone does not grant cleanup permission. Canonical
journals use explicit retirement below. Initial lease/pending groups use the
separate artifact archive operation described next.

## Archiving initial artifacts without a canonical journal

```python
from easysewer.runtime import archive_run_recovery_files

saved = archive_run_recovery_files(
    "/absolute/output/directory/.easysewer-recovery-<token>.json",
    reason="Preserve the reviewed initial write failure"
)
print(saved.state, saved.archive, saved.retained_files, saved.issues)
```

The argument is the expected canonical path, which must be absent. This is an
explicit artifact-maintenance decision, not an inference that a filename or PID
proves ownership of a run. It requires the matching initial lease to exist with
empty or one-byte initial content. It acquires that lease and copies its original
bytes and all matching immediate pending files to a new adjacent ZIP. Pending
contents remain opaque, even when they contain valid run JSON, paths or PIDs.
No output, output reservation, backup or simulation workspace is touched.

The ZIP stores each file's original name, identity, length and SHA-256, plus the
reason and local operation bindings. It is published exclusively and flushed
before any source path is removed. The old lease is then revoked by changing
its path identity while locks remain held: its previous inode is retained under
a private pending name, and a separately locked immutable archive guard is
published at the original lease path. The guard binds the ZIP's hash and its own
file identity. A delayed initial writer fails its existing lease identity check.
On Windows a live creator's open handle can prevent revocation; the function
returns `archive-blocked`, keeps the ZIP copy and leaves the initial source
files in place. It does not stop that creator. The explicit file-management
handle allows delete sharing, while the creator's sharing restrictions remain
effective; see [CreateFileW sharing rules](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).

After the guard is published, only archived pending files with matching identity
and bytes are removed. The ZIP and guard are rechecked before source removal;
changed or added files remain with diagnostics. An interrupted preparation or
revocation can be resumed when its fully written guard, ZIP and original lease
or revocation staging provide matching evidence. Two competing archivers cannot
enter the same transition. A missing lease without that evidence is refused.
The immutable plan needs no per-deletion progress writes: a missing original
pending file is already finished; a replacement is retained.

`RecoveryArchive` reports the expected `journal` path, the ZIP `archive` path,
`reason`, archived member names, `retained_files` and `issues`:

- `archived`: eligible pending sources have been removed. The ZIP and immutable
  guard remain as evidence; a new independent Runner reservation can proceed.
- `archiving`: matching sources remain because removal was not completed.
  Retry the same call and reason.
- `archive-conflicted`: changed/unrecorded files or a new canonical journal
  require review; they are retained. A missing or corrupted ZIP/guard can instead
  raise a validation error and appear as `unavailable` in directory discovery.
- `archive-blocked`: a completed copy exists, but the initial lease could not
  be revoked. There is no claim that the writer has exited or was cancelled.

`max_bytes` defaults to 64 MiB and bounds the complete ZIP read, including its
manifest/headers, as well as bounded source reads. Increase it explicitly for
large remnants. It is not a process-memory limit. ZIP contents are validated
without extraction. A failed attempt may leave a completed copy alongside the
original files; discovery lists these copies, but an unattached ZIP is not
permission to delete anything. Keep the source guard and ZIP together in their
recorded directory for resumable management. This is local maintenance evidence,
not a portable RunResult or checkpoint.

Existing canonical journals, unknown lease bytes, missing leases without a
verified interrupted archive, symlinks and unrecognized directory artifacts are
not silently repaired or discarded. Use canonical recovery/retirement where
valid, and preserve unverifiable artifacts for explicit diagnosis. In particular,
this operation does not manufacture ownership for old PID-only output locks.

Ordinary Runner writers use journal version 5; explicit retirement writes version
6. A complete reservation is first written
and flushed to an adjacent private `.easysewer-reserve-<token>` file. Its identity
and content digest are recorded before an exclusive hard link installs the
destination lock. The private source is then removed. A crash while writing
that source cannot leave an empty destination lock blocking a later run.
The filesystem must support local hard links as well as the lease locking
semantics below; unsupported operations fail without replacing old outputs.
Reservation records are limited to 128 KiB before publication.

```python
from easysewer.runtime import inspect_run_recovery, recover_run

journal = "/absolute/output/directory/.easysewer-recovery-<token>.json"
inspection = inspect_run_recovery(journal)
print(inspection.state, inspection.phase, inspection.targets)

if inspection.state == "interrupted":
    recovered = recover_run(journal)
    print(recovered.state, recovered.issues, recovered.workspaces)
```

Both functions accept `max_bytes`, a positive integer source-byte read budget
that defaults to 64 MiB. For a known large journal, supply an explicit larger
budget to both inspection and recovery, for example `max_bytes=128*1024**2`.
This bounds each journal read, not process memory or the sizes of output files.
Large failure messages and large directory inventories are preserved by the
writer; exceeding the default read budget is an explicit refusal, not lost data.
No recovery write occurs when the initial journal exceeds the supplied budget.

Version 1, 2, 3 and 4 journals remain readable. Inspection leaves their bytes unchanged;
recovery upgrades the record to version 5 when it writes progress. Version 1
reservations retain their original marker and identity checks because no full
reservation digest was captured. Even for legacy records, release checks that
the reservation still matches the bytes observed by this recovery attempt.
Old readers reject newer versions instead of assuming they understand them.
Version 6 records an irreversible decision to retain artifacts and end automatic
recovery. Readers that support versions 1–5 reject it before any file changes.
Version 1/2 workspace records have no cleanup authorization and remain preserved.
Version 3 retains its recorded post-execution cleanup authorization; migration
does not grant any older workspace permission for automatic crash cleanup.
Version 4 retains its recorded worker identity and retention policy; migration
does not invent execution admission evidence for an older worker.

Use the actual path recorded in a reservation or found in the output directory.
Inspection is advisory: `recover_run` independently acquires an exclusive OS
lease and rereads the journal before making changes. An active owner or another
recoverer causes an `OSError` and no recovery writes. PID reuse and process age
do not determine whether a run is abandoned. Windows byte-range locks and POSIX
file locks release on process exit. This requires a filesystem supporting the
corresponding cooperative locking semantics; arbitrary shared/network filesystem
or cross-OS simultaneous access is not qualified.

Before a destructive output replacement, the journal is flushed with the old
file's identity/content, the complete prepared output and its planned backup.
Recovery reconciles those records with the actual files:

- Before commit, restore verified old outputs and remove verified new outputs.
- After the commit record, keep verified published outputs and finish backup
  cleanup.
- Release only reservations belonging to this journal. Ordinary old-format
  PID-only locks have no sufficient recovery evidence and are not automatically
  deleted.
- Recheck reservation identities and content immediately before release,
  including after output hashing and journal writes. Normal Runner cleanup
  follows the same rule. Replacement reservations remain in place.
- Preserve changed targets, backups, locks and incomplete copies. Return
  `state="conflicted"` with reasons and leave the affected reservations held.
  Other independent targets may already have recovered. Retry after explicitly
  resolving the conflict; unchanged file identities and bytes remain necessary.
- Persist each recovered target before releasing its lock, allowing interrupted
  recovery to be retried. Successful recovery removes the journal and lease, so
  further inspection of that path raises `FileNotFoundError`.

The latest recorded phase, original failure (when available), target paths and
workspace paths remain inspectable. `RunRecovery.failure` is the tuple
`(stage, exception_type, message)` or `None`; it does not fabricate a Python
exception for an abrupt OS termination. Ordinary operational failures still
return the existing full `RunResult`.

## Keeping the current files and ending recovery

When a conflict cannot or should not be rolled back, explicitly choose to retain
the current files:

```python
from easysewer.runtime import retire_run_recovery

receipt = retire_run_recovery(
    journal, reason="Keep the reviewed external output and partial evidence"
)
print(receipt.state, receipt.retained_reservations, receipt.issues)
```

This candidate operation requires a valid canonical journal and its matching OS
lease. It refuses an active owner. A nonempty `reason` is mandatory and becomes
part of the durable decision. It retains all outputs, backups, partial publication
copies, private reservation-source files and workspaces. It does not open their
contents, revoke execution admission, stop a worker, or authorize deleting a
retained workspace. Uncertain or still-active private workspaces can therefore
remain in use; manage those resources separately from output reservations.

Before releasing any output reservation, it writes version 6 to the canonical
journal. From that point, `recover_run` can only continue retirement; it cannot
restore an old output or perform workspace cleanup. An earlier reader refuses
the journal. The existing phase, commit flag, original failure, target records,
workspace records and prior issues remain available. This decision cannot be
reversed by passing a different reason on a later call.

Only a reservation matching the recorded journal, token, target, identity and
available content evidence is released. Its identity and complete byte digest
are saved again before removal, including for legacy journals. Parent identity
and reservation bytes are rechecked before release. Replaced or edited locks,
and locks beneath a moved/replaced parent, are retained with diagnostics. A
terminal `retired` state does **not** mean every target is free for a new run;
`retained_reservations` reports locks that were not safe to release. Ordinary
reservation rules still protect those targets.

Transient access or removal failures return `retiring`. Retry with `recover_run`
or the same `retire_run_recovery` reason. Process exit before or after a release
can also be retried. Once a reservation is recorded as released, absent or
retained, subsequent calls do not touch it; this protects a later run's lock.
If a new lock appears after an unrecorded release, its different evidence is
retained and reported instead of removed.

The journal and lease deliberately remain as the local receipt. Inspection and
directory discovery report `retired` after completion, and repeated recovery is
read-only. `retirement_reason`, `released_reservations`, `retained_reservations`
and `retained_artifacts` supplement the usual `RunRecovery` fields.
`retained_artifacts` lists recorded backup/temporary/source/workspace paths;
it is not a claim that each path still exists or that its contents are unchanged.
Historical output-parent identities can remain in a terminal receipt even after
those parents move; no later lookup of those reservations is performed.
The receipt remains a local record at its canonical journal path, not a portable
archive. Preserve it with the retained evidence.

Before ordinary workspace cleanup, Runner confirms that execution has ended,
captures the directory identity and complete file/content inventory, and flushes
that cleanup authorization to the journal. Bundled process sessions additionally
use a known process return code or independently revoked execution admission;
third-party sessions rely on successful
completion of their context cleanup contract (and an integer return code if
they expose that property). A failed or uncertain shutdown without admission
proof does not authorize deletion. Failure before any session request is also eligible.
If the native session factory fails before returning an object, Runner can still
revoke its admission and clean safely. A held or inaccessible admission lock
retains the workspace and journal without replacing the original failure.

If deletion fails, Runner keeps the original run status and primary failure,
adds `run.workspace_cleanup`, records the path in `retained_directory`, and
preserves the journal. `recover_run` retries authorized cleanup.
If cleanup was requested but shutdown or inventory capture could not be verified,
recovery must first establish the crash-cleanup conditions below; otherwise it
retains the journal as a conflict without deleting that workspace.
Remaining files must match the recorded identities and bytes; already removed members need not
be recreated. Added/modified files, substituted roots and special files are
retained as conflicts. Cleanup can itself be interrupted and retried. The
returned `cleaned_workspaces` identifies completed removals; `workspaces` remains
the historical list of recorded paths. A later unrelated directory recreated at
an already completed path is not deleted.

Deliberately retained failed-run artifacts are not authorized for cleanup.
With `keep_failed_artifacts=False`, version 4 records permission to reclaim the
private workspace after a parent crash. Before requesting a session, Runner
records `starting`; after entering it and before opening the model, it records
`active` and the bundled worker's creation identity. The worker captures its own
identity, and the parent validates that it describes the launched process.

Version 5 adds a revocable execution admission file inside the private workspace.
Runner creates and flushes it, records its identity and token in the journal,
and only then requests a session. The bundled worker acquires its exclusive OS
lock and checks the receipt before constructing the native solver. It holds the
lock through native cleanup. A missing, replaced or revoked receipt refuses
entry. The parent also requires an acknowledgment of that admission token.

Recovery acquires the same lock, writes and flushes a revoked marker, records
revocation in the journal and then captures the cleanup inventory. A worker
already using execution resources prevents recovery from acquiring the lock.
A delayed worker, including one that opened the receipt before recovery, checks
the revoked marker or missing file after acquiring the lock and cannot enter.
This closes the gap before the worker's creation identity reaches the journal.
It proves that participating execution cannot use the workspace, rather than
claiming that every associated process has necessarily terminated. Recovery
never sends a termination signal. On Windows, an unadmitted worker's open file
or working-directory handle can temporarily prevent deletion; revocation stays
in effect and cleanup can be retried after that handle closes.

This contract applies to the built-in native session factory, including an
inherited unchanged factory. An overridden third-party session factory does not
implicitly participate or receive the private admission argument. Low-level
sessions outside Runner continue to own their paths and have no automatic
Runner recovery journal. A failure while creating admission, before recording
it and launching a session, leaves the workspace in the recoverable not-started
state. Changed or malformed recorded admission files remain conflicts.

For version 4 and nonparticipating sessions, a fresh recovery process uses
read-only OS inspection to distinguish the same
live worker from an exited worker or a reused PID. Windows binds the PID to its
process creation time and queries the process object's exit state. Linux binds
the PID and start time to the boot ID and PID namespace; a zombie is no longer
executing. Recovery never terminates a worker. An active worker leaves a conflict
that can be retried after exit. Access errors, a changed Linux boot/namespace,
missing identity or a `starting` record remain conflicts, even if the worker
appears absent. A crash before any session request requires no worker check.
Third-party sessions without a worker identity retain the existing normal
context-cleanup contract but cannot authorize this automatic crash reclamation.

Only after revoking execution admission, proving exit, or establishing that no
session was requested, recovery captures
the current inventory of the recorded private workspace, checks its root
identity and persists cleanup authorization before deletion. Subsequent retries
use that inventory and the unchanged identity/content checks above. This initial
capture covers the private directory's contents at recovery time; it cannot
distinguish worker files from files manually added there before capture. Do not
use a private execution workspace for unrelated files.

The read-only identity mechanism follows Microsoft's
[GetProcessTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes)
and the Linux kernel's [/proc process information](https://docs.kernel.org/filesystems/proc.html).
Tests include fresh recovery processes while a real bundled worker is held at
EOF, recovery after its exit, explicit retention, and the former startup gap.
Additional tests cover delayed admission, already-open receipt descriptors,
parent termination during native load, load failure, and recovery interruption
after revocation but before inventory capture.
They do not establish termination latency for every blocked native operation.

Recovery does not resume simulation or certify partial native outputs. Use an
independently saved Runner checkpoint for continuation. The remaining initial
transaction lease/journal windows and explicit resolution of unrecoverable
ownership conflicts are separate work.

Recovery requires the same host platform, unchanged parent directories and
recorded file identities. Do not move the journal and guess translated paths.
Malformed, moved, substituted or over-budget records are rejected. An incomplete
private reservation source or output copy can leave insufficient evidence; that
case is reported for explicit inspection, not guessed away. An incomplete
reservation source does not itself reserve the requested output. A subsequent
run can use it, and recovery of the old record will preserve the new run's lock.
Journal files are flushed before replacements, but this is tested process-exit
recovery, not a guarantee against power loss, disk corruption or hostile
concurrent modification. Publication is still visible one output at a time.
