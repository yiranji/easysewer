# 2.0 Runner and execution records

`Model.run()` and `Runner.run()` connect Model, RunConfig, resource preflight and the isolated backend. They return an immutable RunResult for operational failure as well as success.

For cached hydrology, see [production-condition comparisons and explicit reuse
intents](2.0-cache-conditions.md). The execution record now retains these
comparisons separately from cache layout/provenance and result applicability.

```python
from datetime import timedelta
from pathlib import Path
from easysewer.model import Model, FileReference, Ref
from easysewer.runtime import RunConfig, ReportReadOptions

model = Model.from_inp("network.inp", strict=True)
config = RunConfig(
    output_directory=FileReference(path=str(Path("runs/demo").resolve()), direction="output"),
    wall_time_limit=timedelta(minutes=10),
    native_call_timeout=timedelta(seconds=30),
    report_read=ReportReadOptions(tables=("swmm:node_depth", "swmm:node_flooding")),
)
result = model.run(config)
result.raise_for_status()
print(result.output.path, result.mass_balance)
print(result.output_metadata.names("swmm:nodes"))
```

Only supply a report encoding when it is known. The default preserves raw bytes
and tries strict UTF-8/BOM; for bundled 5.2.4 backends, a producer profile can
normalize known ANSI superscripts in volume headers while retaining byte offsets.
Unrelated decoding failures leave `text`/`encoding` unset and produce a diagnostic.
It never guesses a code page or drops bytes. `on_decode_error="raise"` instead
fails the run before publication. Native completion alone does not certify hydraulic accuracy or
acceptable continuity; mass-balance percentages remain the actual native values.

## Captured inputs and execution

The Runner first copies the Model, probes actual backend capability and checks
the complete profile. Do not mutate the Model concurrently while that initial
copy is being taken. Later edits, including edits from progress callbacks, cannot
change the captured Model. The caller supplies trusted Python backends and data
inspectors explicitly; the worker is a lifecycle boundary, not a security sandbox.

Every file reference must have an unambiguous registered consumer. Unknown
sections with unresolved resource effects block execution. Active input files
are copied into an owned workspace, hashed and inspected there. The sources
are also hashed again after copying: file identity, size and timestamps alone
cannot detect every same-size write on a coarse filesystem clock. This adds a
streamed source read and rejects inconsistent captures; it is not an atomic
filesystem snapshot against arbitrary concurrent writers. Required inputs
must pass complete format inspection within `file_inspection_limit` (64 MiB by
default); an incomplete inspection blocks the run. Missing optional resources
warn; inactive resources are represented by inert private paths. Files opened
by native SWMM in update mode use writable copies, preserving read-only originals.

References in the execution copy point to short ASCII relative paths. The INP
is explicitly UTF-8 and receives another native document check after encoding.
The original Model JSON retains original paths/encoding/provenance. Resource
bytes stay exact. Only the native worker changes its cwd, so Windows directories
containing Chinese characters or emoji do not require passing their prefix to
the native file-name API. General foreign-platform path translation is rejected.

Model `TEMPDIR`, when supplied, selects the parent of a new private execution
directory; the engine uses its owned scratch subdirectory. Otherwise the output
directory is the workspace parent. Relative resource bases come from the input
document, explicit RunConfig input directory, or explicit `relative_to` context,
according to each consumer's declared base. There is no implicit search for a
missing file elsewhere.

`RunSnapshot` records immutable original Model/config JSON, actual executed INP,
SHA-256 digests, resource identities, fixed profile, effective options, units and
actual backend bytes. `snapshot.model()` restores an independent original Model;
extension models require their schema when restoring. Its original references
do not automatically point at archived assets. The published INP references the
captured asset directory and can be run again while those assets remain present.

## Ownership, cancellation and failure

Output destinations are reserved before native open, including INP/RPT/OUT and
declared FILES/LID outputs. Existing files require `overwrite=True`. Input aliases
and conflicting output ownership are rejected, including existing hard links.
Explicitly declared output directories may own declared child outputs; unrelated
or input-containing output roots remain conflicts.
Adjacent exclusive reservation files coordinate cooperating Runner instances,
even when a declared output lies outside the main output directory. Destination
identity and streamed content checks detect external changes between reservation
and publication, including same-size writes with unchanged timestamps. Reservation
hashing and publication verification include cooperative cancellation checkpoints.
File preflight also checks cancellation and the whole-run deadline while reading
chunks and traversing built-in input formats. Cancellation at this stage retains
the `preflight` failure stage and follows the normal output protection, workspace
retention and lock cleanup policy. Custom inspectors keep their existing call
signature and are checked before and after invocation; arbitrary custom code or
a blocking system call is not forcibly interrupted.

The `report_read` phase also checks the event and whole-run deadline during RPT
chunk reads, line scanning and built-in table parsing/validation. Interrupted
report work preserves the previous publication and reports `report_read` as the
failure stage; `native_completed` can already be true. Cancelled/timed-out runs
capture at most `min(report_read.max_bytes, 64 KiB)` of the failure report and
label any truncation. Complete retained files follow the normal retention policy.
This avoids parsing the entire report again after interruption. Required cleanup
and retained-artifact hashing still run, so cancellation is not instantaneous.

The Runner writes privately and prepares all destination copies before replacing
requested files. Ordinary publication failures roll back earlier replacements.
Before commit, prepared copies and published outputs must match their captured
bytes and identities. Resource directories also bind their complete file and
directory membership, including empty directories. Rollback checks this evidence
before deleting a published file or tree; changed outputs remain in place. Original
backups are checked before either restoration or deletion, and changed backups
are retained. Cleanup diagnostics identify these conflicts while preserving the
primary publication failure. Restored checkpoint streams likewise verify the
startup destination's content before collection. These checks add streamed reads
of existing destinations and publication copies; they do not retain whole output
files in memory. This is exception rollback across files,
not simultaneous multi-file visibility. Local process-crash recovery is explicit:
see [run recovery](2.0-run-recovery.md). A flushed journal records planned
replacements and content evidence before publication, with an OS lease preventing
recovery while the owner is alive. Conflicts retain their reservations, journal
and backups instead of allowing another run to overwrite recovery evidence.
Power-loss durability and automatic stale-lock deletion are not promised. These
checks do not defend against a hostile process with write access to the same
directories.

Successful runs publish a unique `easysewer-assets-<run_id>` directory alongside
the main outputs. It contains captured resources, separate copies of declared
outputs and execution evidence. `FileArtifact.read_bytes()` checks the stored
hash and size. A declared output artifact points to its run-specific archived
copy and records the separately requested destination in `declared_path`.
Later runs may overwrite a requested destination but cannot silently change the
older artifact's meaning.

The default `keep_failed_artifacts=True` retains only the private workspace;
`retained_directory` locates it, and any returned partial artifacts have
`complete=False`. False requests owned cleanup. A failed run never deliberately
publishes partial native files over a previous success. Cleanup warnings remain
separate from the primary failure. `native_completed=True` means end/report/close
finished successfully; report decoding or publication can still fail afterward.

If requested workspace cleanup fails, `retained_directory` also records its
historical location and `run.workspace_cleanup` explains the failure, including
on an otherwise successful run. Runner preserves the recovery journal rather
than losing the pending cleanup. Once execution shutdown is confirmed, a flushed
identity/content inventory authorizes safe retries through `recover_run`; added
or modified files are retained as conflicts. Unconfirmed shutdown or an incomplete
inventory keeps the journal without authorizing deletion. See
[run recovery](2.0-run-recovery.md) for the versioned record and remaining
parent-crash/worker-exit limits.

For a parent crash with `keep_failed_artifacts=False`, the current journal also
records execution admission before launching the bundled worker. The worker
locks and validates that receipt before native load and holds it through cleanup.
Explicit recovery must obtain the same lock and durably revoke admission before
reclaiming the directory; a delayed worker cannot enter afterward. Worker creation
identity remains a fallback for older records and nonparticipating factories.
An active execution lock or changed receipt leaves a conflict. The default
retention policy continues to preserve failed-run workspaces after a parent crash.

Statuses are `succeeded`, `rejected`, `failed`, `cancelled` and `timed_out`.
Bad API argument types raise directly. `raise_on_error=True` raises `RunError`
with the result and original exception as its cause. `result.raise_for_status()`
is useful for the normal return-value path.

Progress callbacks receive immutable `RunProgress` values for preparing, opening,
running and finalizing. The first/final running updates are emitted even for short
simulations; intermediate updates respect `progress_interval`. Callback exceptions
fail the run and trigger cleanup. `step_batch_size` controls native work per RPC.
An event with `is_set()` supports cancellation; in-flight native calls are checked
at `cancellation_poll_interval`. The whole-run deadline includes preparation and
publication, while `native_call_timeout` bounds each worker RPC. Cleanup has its
own bounded wait. Arbitrary blocking Python callbacks/inspectors or host filesystem
calls cannot be preempted by cooperative checkpoints.

## Cache evidence and persisted execution

SAVE HOTSTART, RUNOFF and RDII create `ProducedCache` records from actual output
bytes, the actual executed INP hash, loaded library hash and typed layout. Native
identity order is checked before recording this evidence. A later run can pass
`producers={"HOTSTART": evidence}` (or RUNOFF/RDII) when its USE file references
those bytes. It verifies the evidence artifact, consumed bytes, engine and target
layout. `consumed_caches` distinguishes Runner-observed provenance, caller-asserted
manifests and format-only inputs. Caller manifests remain supported explicitly.

These layout checks alone do not establish physical reuse compatibility after
changes to rainfall, parameters, time windows or omitted state. RUNOFF now has
a separate captured-condition policy: changed/unknown conditions warn with
`run.cache_physical_scope` under the default intent, or reject under
`require_match`. Explicit `frozen` history retains its comparison and warning.
HOTSTART is not a complete checkpoint, and RUNOFF can
omit LID-specific routing/removal behavior. Large produced caches may have their
provenance recorded without full payload inspection when the configured budget is
exceeded; a consumer still requires complete input inspection.

The published execution directory includes original `model.json`, `config.json`,
actual `input.inp`, cache manifests and `execution.json`. The execution record
contains run/time/profile/backend information, hashes, resources, actual native
identities, OUT metadata, RPT decoding/table artifacts and mass balance. It records observed native execution,
not a signature or publication-success attestation. For complete typed result
persistence, use [RunResult.save/load](2.0-result-archive.md), which captures the
returned final status and registered artifacts separately from this execution
record. Authenticated producer exchange remains separate work.

The bundled standard engine fixes the former Linux multi-pollutant/land-use
[HOTSTART writer defect](2.0-hotstart.md). Runner still checks the resulting
layout before publication and rejects malformed legacy files. This format fix
does not make HOTSTART a complete simulator checkpoint.

## Results and remaining gates

`engine_objects` comes from the loaded engine's identity API. `output_metadata`
comes independently from the actual OUT header/footer and REPORT-selected IDs.
`OutputMetadata.index(Ref(...))` raises `NotRecordedError` for an object absent
from that OUT, even when the engine simulated it. Metadata checks completion,
counts, units, variable codes, frame widths and first/last times; it does not
read every result value or validate all intermediate timestamps. Its reader is
pure Python and bounded separately from whole-file result reads.

[OUT series](2.0-output.md) are available through `result.open_output()`, with
artifact verification, actual ID/pollutant mapping, units and captured sampling
semantics. [RPT tables](2.0-report.md) provide 43 summary/status/input
codecs, source units/precision, explicit missing statuses and extensible registries.
`result.report_reader()` queries captured object observations and additional
summaries; `result.read_lid_report(owner)` verifies archived LID detail files.
Unregistered table keys are rejected explicitly. ReportDocument retains the
bounded RPT in memory (64 MiB source-byte limit by default). Failed runs retain a
separate `failure_report` best-effort capture before workspace cleanup, with
explicit prefix truncation and raw error context. It never publishes successful
tables or replaces the primary failure. Local output transaction journals now
support explicit process-crash recovery, residual discovery and retirement.
Known initial lease/pending-file residues support explicit raw-byte archival;
unverifiable ownership remains preserved/refused. Broader physical result
qualification remains open.
[FlexiblePonding](2.0-flexible-ponding.md) now has a captured backend plan, explicit
OUT semantics, removal totals and private trace artifacts. Its adjusted native
statistics and water/quality accounting have independent balance tests. [Directory-consumer adapters](2.0-directory-resources.md) capture bounded private
trees and support result/checkpoint evidence and transactional publication. Their
final installation and full-scale performance qualification, complete migration,
actual browser/WASM execution and overall release gates remain open.

Tests compare full OUT bytes with independent direct-native runs, rerun published
inputs, change original resources after capture, exercise overlapping runs and
publication failures, consume three cache kinds, and check all eight LID outputs.
The OUT layout reference is official tagged
[SWMM 5.2.4 output.c](https://github.com/USEPA/Stormwater-Management-Model/blob/v5.2.4/src/solver/output.c).

Execution-record construction participates in the run's cancellation/deadline
scope before output publication. Built-in record cloning, table conversion,
pretty JSON encoding, object parsing/validation and private artifact writes
check between batches. Interruption retains the `publication` failure stage
and the existing rollback/failed-artifact policy. Private writes detect short
writes; partial private records are never published as successful outputs.
`ResultTable.to_json_document(checkpoint=...)` also accepts an optional no-argument
callback and preserves its exception object and chain. With no active callback,
serialization retains the standard-library path and existing JSON 1.1/1.2 bytes.

These checks do not preempt a single system call, allocation, scalar encoding,
or arbitrary extension operation. JSON's C parser calls back at object boundaries;
a large scalar-only array or string has no internal object callback. Mandatory
rollback, resource shutdown and full retained-artifact verification still take
time after cancellation. The complete resource/performance matrix, including
mandatory cleanup and retained-file verification latency, remains open.

Initial model copying is inside the run failure boundary and follows the first
cancellation/deadline check. An already cancelled run does not copy the model,
create an output directory or open a backend. Copying and initial validation
failures use the `validation` stage; run-input validation uses `preflight`.
Runner activates the work scope around the existing `copy()` and `validate()`
calls without adding keyword arguments to extension overrides. Cancellation
inside those operations keeps the caller's model and existing outputs intact;
required cleanup and failed-artifact retention still follow the run policy.

Runner also activates the scope for initial model/configuration JSON capture and
model fingerprinting, using the existing `to_json_document()` call without new
arguments to extension overrides. Interruption here retains the `capability`
failure stage, before resource inventory, output directory creation or native
execution. Built-in source merging, preserved JSON cloning/comparison and shape
checks can stop during large captures. Existing outputs and the caller's model
remain unchanged; scalar/C/OS calls and arbitrary extension code retain the
boundary limits described in [Model JSON](2.0-json.md).

Preparation now inherits the cancellation/deadline scope through built-in file
consumer discovery and recursive file-reference traversal, private resource
rebasing, INP generation/reparse/validation/private writes, and cache facts and
artifact verification. Existing extension `to_document()` call arguments stay
unchanged. Private INP short writes report the correct artifact context.
Immediately before opening a session, Runner compares the private INP with the
captured bytes in bounded reads, including EOF; truncation, extra data and any
byte change are rejected. Resume parsing and consumer reconstruction inherit the
same scope. This does not make the input an atomic filesystem snapshot against
arbitrary concurrent writers.

Preparation failures retain their actual phase: `inventory`, `capture` for
resource staging, `preflight` for INP/cache preparation, `checkpoint_prepare`
for resume reconstruction, and `open` for final input verification. Existing
outputs, producer artifacts and saved checkpoints remain protected by the
existing retention/cleanup and failure-archive rules. Mandatory rollback and
cleanup can continue after the cancellation request; no fixed total-return
latency or full resource/performance qualification is implied.

Result finalization also inherits the cancellation/deadline scope through
built-in result-context construction after `session.end`, post-execution INP
comparison, OUT identity/property parsing and identity checks, report context,
cache layout/payload/manifest work, and pre-publication artifact collection.
Post-execution INP comparison uses bounded reads and verifies EOF, preserving
rejection of truncation, extra bytes and changed content.

A result-context interruption has failure stage `end` and does not claim the
full native lifecycle completed. OUT/input verification interruptions have stage
`verify`; producer cache/manifest interruptions have stage `publication`. After
the session has completed, `native_completed` can be true while the overall run
is cancelled or timed out. Existing published outputs remain protected, and
retention, cleanup and failure archive rules still apply.

The inherited finalization scope exits before transactional publication. Once
publication has committed, a newly set cancellation event does not convert the
published success into failure. Mandatory rollback, session/worker shutdown and
retained-file verification remain required and can extend total return time.
The individual traversal checks do not establish a full Runner latency bound or
complete resource/performance qualification.

Explicit file and directory inspection callbacks preserve their original exception
objects and cause chains. In Runner, an ordinary callback exception fails
preflight; `raise_on_error=True` raises `RunError` from that exception. Inspectors
should return an `InterfaceInspection` report for invalid content. Framework
path, budget and content-change errors retain their resource diagnostics.
